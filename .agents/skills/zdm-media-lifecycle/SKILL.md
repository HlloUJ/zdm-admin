# 装点猫媒体生命周期

## 目标

所有客户端和业务模块共用平台媒体服务，但业务数据与媒体引用按客户端、租户、门店和业务域隔离。媒体组件只负责选择、预览、删除等交互，不直接决定文件名、存储位置、引用状态或物理删除。

## 接入规则

- 上传统一创建 `media_assets` 临时记录并返回媒体 ID；业务表只保存媒体 ID，响应 URL 由媒体服务生成。
- 业务保存必须在同一事务内写业务数据并调用 `MediaReferenceService.replace` 更新 `media_references`；成品现货与大板使用独立业务域，不能共享业务表或价格体系。
- 替换、移除或彻底删除业务数据时，先提交业务事务，再创建清理任务；清理工作器必须重新确认全平台引用数为零，才能删除物理文件。
- 取消新增或取消编辑时，前端释放本次上传且尚未引用的媒体；释放失败不能伪装成业务保存失败，由后台重试和午夜任务兜底。
- 视频封面作为独立图片媒体登记，通过 `derived_from_media_id` 关联源视频；交互层不得把 Base64、Blob URL 或本地路径持久化为业务数据。
- 每个新客户端仍调用同一媒体服务，但上传、引用和读取权限必须使用当前身份的 `clientCode`、`tenantId`、`storeId` 校验，不能信任前端传入的归属字段。

## 清理规则

- 实时清理：替换、移除、取消上传和业务数据彻底删除后触发。
- 定时清理：每日 00:00 扫描登记媒体；启动时若超过 24 小时没有成功记录则补跑；多实例通过数据库锁保证只有一个执行者。
- 自动清理只处理媒体登记表中已确认无引用的文件。来源不明、未登记物理文件必须先通过 `/api/admin/media/audit` 与数据库业务字段、代码静态资源进行三方核对，并取得本次明确删除授权后按精确路径删除。
- 回收站中的业务仍视为有效引用；共享文件只要剩余一个引用就不能删除。
- 物理删除失败不回滚已经成功的业务保存；记录失败原因、重试次数与下次重试时间。

## 验证

- 覆盖上传可读、业务绑定、替换后旧媒体回收、共享引用保护、取消上传、过期临时媒体午夜回收、启动补偿和删除失败重试。
- 迁移前备份并持有项目数据库迁移锁；迁移后核对 `media_assets`、`media_references`、业务媒体 ID 与物理文件。
- 清理前后分别执行媒体审计；完成状态要求未登记物理文件、登记但缺失文件、登记但无引用文件均为零，除非逐项说明保留原因。

# 任务续接登记与准入（284）

## 目的与边界

任务登记并不等于允许自动执行。Git 登记只能证明本地任务归属，不能证明云端原 worker 当前存在。本补充把未来任务的明确登记、只读准入和根线程交接连起来，复用既有续接执行器，不另建任务执行框架。

其他任务的用户暂停仍有效；新增登记默认只观察、不续接。不能因为 284 已发布、监测定时运行或旧 worker 不可达，就自动解除暂停、替换 owner 或恢复其他任务。

## 登记流程

1. 原 worker 在原工作区，通过原任务工具保存准确 checkpoint。登记请求读取真实 registry、HEAD、原 owner、授权来源、根线程、worker 路径及任务编号/名称/稳定 ID。不能从 owner UUID 猜 worker 路径。
2. 请求是不可变记录。根线程须以平台实际读取核实原 worker 身份与授权范围，保存相应凭据；本地 JSON 不能独立证明云端身份。
3. 接受请求前重新读取 registry、HEAD、策略、激活回执、全部绑定以及普通开发控制记录。任一版本/内容发生变化，旧快照拒绝，重新核验；不得拿旧批准自动刷新快照。
4. 排他地追加同一任务的观察绑定，默认 `observationOnly=true`、`resumeAllowed=false`，不覆盖原绑定、owner、暂停或已完成状态。重复请求核对已存在结果，未知写入结果及遗留锁保留供核验，不擅自清锁重放。

## 每轮监督

- 使用真实磁盘输入产生观察与阻点，不把调用者提供的状态当成现场。
- 激活回执、策略或绑定缺失/不一致时仅观察，不派发。
- 全局暂停、任务暂停、普通开发控制暂停、已关闭、缺原身份、过期 checkpoint、HEAD/登记版本变化、未知旧效果均阻止执行交接。
- 同一 Git 任务即使对应多个看板编号，也只有一个执行单位；不能为各编号重复唤醒。
- 输出的 handoff 只是“需要根线程重新核验”的候选，不是执行授权。原根线程仍须实时核对原 worker、资源、原执行结果及用户最新指令，独占 claim 后才通过受支持的原入口继续。
- 原 worker 树丢失、平台不可达、Mac 离线或进程证据不可得时失败关闭。监测可报告准确阻点，不冒称已续接。

## 通知与完成标准

沿用 `task-recovery-notice.mjs`。真实新进程 spawn 与精确 task/checkpoint/attempt 绑定后才能报告“成功续接”；消息发送成功不代表业务成功。失败通知只写已核实原因，未知写“待查”。实际 ChatGPT 消息读回后持久 receipt，未知投递不得盲目重复。

发布代码、定时轮次读取成功、绑定接受、允许执行、实际新执行分别是不同状态。只有准确任务全链路证据齐全才报告该任务接入；不能声称所有旧任务已经覆盖。真实 Mac 重启未经测试，10 分钟定时频率不是恢复延迟保证。

## 隔离验收

覆盖原身份/授权字段不匹配、快照与暂停并发变化、重复接受、遗留锁、缺回执、已关闭、缺 checkpoint、未知效果和同任务别名去重。隔离测试的云端凭据是测试输入，不是生产身份验证。正式发布后由根线程将监督轮次改为调用已发布的准入读取入口；候选分支模块不直接替换在线监督。

## 可执行只读入口

发布后，在主仓运行 `node scripts/task-continuity-cli.mjs --once --admission`。它读取正式登记和当前策略并返回 `admission.handoffs`/`admission.blocked`，同时写原观察器快照；不会发送消息、claim、启动任务或改变任何暂停。定时根线程应消费该结果，而不是自行从旧绑定拼接执行候选。

当前准入只将具备准确普通开发 checkpoint 的任务列为独立核验候选；正式交付阶段仍须原正式执行器核对效果，不能凭失败日志自动派发。登记模块锁仅协调遵守同一协议的写者，不是跨所有本机写者的事务；监督与控制端仍必须在实际消费时重验，未知竞争保留阻断。

# 已停止旧前端的只读运行引用证明

这是正式工程自升级的只读引用证明入口，不恢复、停止或释放被核查任务的预览、租约、后端和数据。原 `unknown` 拒绝规则默认保持。首次自升级仍遵守 `docs/task-completion.md`：准确已审查候选只进入自身 PR 流程；最终运行交接与清理由准确已发布且 main CI 通过的版本承担。

## 公开入口与来源

在当前交付任务的准确 Worktree，使用已发布入口；首次自升级使用该任务准确已审查 Git 对象的只读载体。直接 `exec node <入口>/scripts/task-completion.mjs reference-proof <另一任务永久ID> <其准确原生rollout文件>`，避免一个仍引用被观察任务的 shell/npm 包装进程留在观察范围内。

入口现场核验真实执行者、当前阶段的交付 admission、既有业务冻结、当前完整提交与原受信源码校验。只接受真实 Codex sessions 路径中属于当前绑定 worker 的原生执行事件：原 `preview start` 已结束；期间原 `preview check` 成功且匹配 Worktree、分支、端口和 API；随后一分钟内的原 `work status` 证明同一干净准确源码。命令必须是原公开入口，不接受调用方 JSON、拼接命令、文字中的 safe/runtimeReady 或未知执行结果。原租约 inode 和创建/变更时间必须证明该文件在原成功 nonce 检查前已存在且此后未改写。

原生产 OS 观察器和数据、后端身份校验器固定加载原已发布 Git 对象的只读快照，不随之后的 main 升级改换观察实现。宿主先用原 Git 对象准备当前任务私有 `task-delivery/<当前任务>/published-observer/<原发布SHA>/` 源码载体，逐 Git blob 核对后封为只读；收集器缺少它时拒绝，不自动创建、修改或替换。每次加载前后再次核对整个目录、全部文件及模式与该原对象一致，且该对象必须在 origin/main 的发布历史内，依赖锁须一致。不提供 exec、环境、进程或文件的 JSON/CLI 注入适配器。新增收集器、默认引用读取器及公开完成入口的实现来源与本任务候选分别准确绑定，见下节；不要求旧业务 Worktree 复制 main 工具。原生历史、租约、源码、登记、Docker 本地上下文、实际容器/挂载/来源记录、原数据库和媒体卷以及备份须能独立关联。

原生执行的终结记录和原退出码（包括 -1 等中断信息）原样保留，不改成成功，也不据此推断操作系统进程已结束；当前是否仍有引用必须另由两轮完整真实宿主观察证明。

当前不解析或豁免祖先进程，只忽略真实观察器自身；其他进程只要命中被观察任务/目录/nonce 就拒绝。`wrapperAncestors: []` 表示没有祖先豁免，不是祖先解析结果。其他已识别前端沿用原元数据策略，不额外要求旧前端提供 runtime nonce；未知已租前端仍拒绝。

返回的 `file` 和 `digest` 指向当前任务 Git common dir 的私有 `task-delivery/<当前任务>/reference-proofs/<id>/proof.json`。它保留两轮完整宿主进程、打开文件、容器和端口观察及相关原生执行事件，终端只显示位置、摘要和数量，不外发原始材料。这里的写入仅限当前交付任务自身证据，不改另一任务源码、index、登记、租约、8082 等后端、数据库、媒体和备份。Git 查询禁用可选 index 刷新。

每次实际观察先在同一私有命名空间建立独立 `observation-<id>` 日志。取得的后端来源对照、完整 OS 清单、前端响应、身份及完整轮次分别在对应断言前落盘；失败保存原错误与堆栈并报告证据目录，不能把失败当作成功证明。事件使用排他创建，不覆盖先前材料；未取得的后续轮次不补造。旧版本首次打开文件断言失败仅留下错误日志，其后的独立观察不冒充首次现场。

## 历史发布基线、收集器与消费者

公开入口保留原两参数形式，另支持 `reference-proof <另一任务ID> <准确native文件> --published-baseline <40位原发布SHA>`。未传仍选择当前 main；原检查发生于较早 main 时应明确提供其原发布 SHA，不自动猜测或回退。该 SHA 必须在 origin/main 历史内，实际 main reflog 必须覆盖真实 native check 时间且当时对应同一 SHA，再加载当前消费者私有命名空间中完整且逐 blob 核对的原 Git 只读观察器快照。没有覆盖、错 SHA 或缺少快照均拒绝，不接受任意 observer 路径。

v2 包分别保存三种身份：原观察器发布 SHA、实际收集器 Git 对象、本任务候选 SHA/树。普通消费者即使旧分支没有收集器文件，也只使用 canonical 已发布 main 的准确实现：main 与 origin/main 一致、干净且实际加载文件匹配该对象。加载后文件变化须换新进程，不把旧已加载代码冒充新实现。只有原 520 工程 ID 的首次自升级保留其准确已审查 `reviewed-control/<本任务候选SHA>` 只读载体特例，其他消费者不能借用候选载体。收集与实时复核前后分别保存准确来源；原 producer 对象的字节和发布历史仍核验。

消费者候选使用当前已发布采集器的完整冻结校验，按现行保护策略与原冻结声明一起校对内容、模式和删除状态。历史发布快照仍负责原生事件时间、现场观察和运行身份核验。较旧观察器的源码分类不会用于重算较新消费者的冻结摘要。

每个消费者须由自己的真实执行者凭有效交付准入，针对原冻结和准确干净候选重新执行完整真实两轮，生成自己命名空间下的新包；不能拿 520 或别的消费者的包放行。旧 v1 包保留为原记录，不按新格式重新解释。

组合 main 导致本任务 HEAD 变化时，控制器在主线合并前明确拒绝原包并保全已组合候选。执行者用同一公开 reference-proof 命令、原历史 SHA 和当前准确 HEAD 生成独立新包，再以新 file 续接 deliver；原包、原冻结和已有 CI 全部保留，不静默改包。仅忽略目录中的证明材料变化不触发新 CI；真实候选输入变化仍按原适用门禁验证。运行交接及收尾始终使用 main CI 通过后的已发布入口。

## 正式交付中的使用

宿主核对准确候选与真实证明后，在原公开完成命令后附加 `--reference-proof <返回的file>`，支持 `prepare`、`deliver` 和中断后的 `settle`。继承给直接子进程的环境内容只有该文件位置、摘要及准确消费任务/目录等选择信息，是选择器而非放行能力；其他任务或隔离测试仓库不会继承该例外，仍执行原 unknown 保护。

准备阶段采集时给 `reference-proof` 附加 `--for-prepare`，并在同一任务 Worktree 运行 `complete prepare <任务ID> <登记HEAD> --reference-proof <file>`。可同时附加原有 `--engineering-review <file>`。引用检查使用当前准备准入，该准入仍只能执行准备阶段允许的动作。若组合登记使 HEAD 变化，原包在推送前被拒绝。用新的登记 HEAD 重新采集证明，再从同一公开准备入口继续。续接在推送前重新检查运行引用。该流程保留原冻结、组合证明、已有 PR 和首次失败。

每次引用边界都重新执行两轮完整真实观察，要求每轮不超过60秒，并前后对照同一租约字节/inode、登记、原生事件、源码/index、Docker/容器、数据及备份身份。旧证明文件只固定被核查对象和审查来源，不能用其旧观察代替当前事实。新轮次原始材料也保存至当前任务私有证据目录。

仅原端口明确 `ECONNREFUSED`、原执行已结束、原 PID 未活动或复用、无残留 task/nonce 进程、无未证明的相关打开文件或 socket、保留后端来源/数据绑定不变且健康、无已识别前端或实际客户端继续引用该后端时，才能把该准确前端记为“已证明停止且租约保留”。不会伪造在线元数据、`closingLeases` 或 `runtimeReady`。其他端口继续原策略，包括既有对无租约无关 HTTP 服务的处理；不扩大未知租约的放行。

### Docker 保留目录引用

macOS Docker Desktop 保留后端可能继续打开源挂载目录。此处只能证明“旧前端已停止、这些目录引用仍在且全部保留”，不能证明后端停止、资源无引用或资产可删除。生产收集器自行调用真实工具，无调用方观察适配器：唯一真实本地 Docker Unix socket 的持有进程必须是 Apple 签名链及 Docker 团队 `9BNSXJN65R` 验证通过的 backend 程序；其他目录持有者只能是同一安装中的已验证 sailor 直接子进程。签名文件的物理身份须匹配实际加载的 image vnode，进程父子、UID、启动时间和查询前后身份须一致，不能按进程名豁免。

原后端容器须唯一挂载该准确物理源目录到 `/workspace`，其他容器的父级或子级重叠挂载均拒绝。逐个 numeric FD 同时核对原完整 OS 清单、额外原始 lsof 设备/inode/只读访问及本机 SDK `proc_pidfdinfo` 的真实 DIR vnode、文件类型、打开标志和路径；fsgetpath 能解析的目录还须由 lstat、realpath 对应同一物理目录。旧 vnode 的 fsgetpath 已为 ENOENT 时，必须原样保留内核目录 inode、链接数、缓存路径及当前 namespace 状态：路径缺失须保留 lstat ENOENT；同名路径已替换则另存当前目录的不同 inode、同设备 DIR 身份与 realpath，不把它冒充旧 vnode。两种情况下真实同设备父目录都须仍能映射到保留源；同 inode 却 fsgetpath 失败或其他错误仍拒绝。不把 ENOENT 或链接数解释为引用失效，不创建或替换路径补证。两轮所有服务、FD、源挂载和 endpoint 身份须完全稳定。REG、cwd、未知 PID、未映射目录、写入句柄、前端 socket 和后端客户端不在此范围。

本机原始诊断有两个 FD 指向同一 namespace 缺失的目录 vnode，另两个 FD 指向同名路径已替换的旧缓存目录 vnode，旧目录链接数仍为 2；这些事实说明目录引用仍需保留。证明包始终 `cleanupAuthorized: false`，本入口及正式交付不得据此停止 Docker、489 后端或清理其源、租约、数据库、媒体及任何目录。

活进程、缺失或异常观察、跨主机/远程 Docker、变化、未知引用、改写/替换/链接材料、来源或授权不符一律拒绝。此能力不授权停止保留后端、删除任何租约或资产，也不等于另一任务已恢复或交付。只读证明不替代原 PR/main CI、冻结校验、主线互斥、运行交接和最终收尾。

这是本地可信宿主与内容来源的可审计保护。尚无独立账号、不可改远程基准和对应必需门禁证明时，不声称它是不可绕过的权限隔离。

## 已中断的最终验证后端

只用已通过主线 CI 的准确发布版，从 main 锚点运行 `node scripts/delivery-repairs/validation-backend-recovery.mjs "<登记的原工作树>" "<任务私有原租约留档目录>"`。两项参数仅定位证据。原执行者、原 final 决定及失败票据、冻结和候选、原 PID、容器 ID、端口、外部引用证明的路径及摘要由已登记对象与留存日志交叉得出。另需已获准定向停用原验证后端。

入口独占当前任务和集成、预览资源，核对已归档的自有前端以及原验证进程组退出，复用完整的两轮实时引用采集，再证明没有其他前端、容器配置或宿主连接指向该验证后端。通过后保留单次停止意图，调用已发布启动器的准确 `--stop`。同一容器对象、原挂载配置、卷、库、备份以及其他已保全运行入口须保持原身份。结果未知时只读回同一意图和对象。成功回执仅证明本次停止，交付票据、准入、Git 和远端检查另走原流程。

Docker Desktop 维护后的原验证后端恢复，由原执行者从发布主线执行 `node scripts/delivery-repairs/validation-backend-recovery.mjs "<任务工作区>" "<原前端租约归档>"`。恢复从该任务的 `task-delivery/<task>/validation-docker-maintenance.json` 读取私有来源选择。选择记录绑定 `version: 1`、原 `task`、`owner`、`head`、`accepted` 和 `archiveManifest`，`records` 中的 `baseline`、`restart`、`recovery` 和 `bindings` 各提供原件 `file` 与 `sha256`。保留首次失败、原租约归档和原后端记录。逐项重算原容器、镜像、配置、挂载、任务数据与源码身份，只有维护中记录的三项空 DNS 数组可用于重算旧摘要。新启动时间须对应原维护日志、同一容器对象和实际应用启动日志。

前端端口已经重新分配时，按现有租约、Worktree、分支和运行 nonce 确认识别为新任务。若新任务也已关闭，选择记录还须有 `records.previewLeases` 和 `reassignedPeer`，后者包含 `task`、`port`、`backendPort`、`containerId` 与 `nativeCheck`。原检查通过的真实 native 命令、主线 reflog、维护前租约摘要、当前容器和两轮完整本机观察共同证明其历史代理和当前已关闭身份。仍有进程、打开的非证明目录、监听、客户端或不明确的租约即拒绝。恢复期间只对经证明的原后端完整容器 ID 发出停用命令。

原任务取得实际准备或最终准入后，仍以普通 `reference-proof` 入口为当前冻结候选生成新证明。原停用回执、阶段日志、原归档和维护原件共同绑定本次特殊来源。已证明的第二个关闭端口随当前两轮现场观察重新核验，供同一原任务的引用检查消费。源码候选、准入范围、已知租约和资产保留的验证继续执行。

410 的 8083 停用后，800 的共享维护又启动了同一 489 容器。410 在原准备或最终准入下仍使用上面的公开命令。收集和消费都重新核对原 8083 停用回执、首次维护选择记录、410 在第二次维护前采集的 5177 证明、800 封存的维护原件，以及 489 原执行者的重登记回执。第二次维护前的启动时间必须精确接上第一次维护后的运行实例。当前 8082 的完整容器 ID、镜像、配置、有序挂载、源码、数据库、备份、5177 租约、实际启动日志和健康记录均须匹配。这个衔接只登记这两个窗口。缺件、归属变化或后续未知启动均保留拒绝结果。

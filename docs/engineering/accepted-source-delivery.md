# 任务完成：本地业务快照与自主技术交付

授权唯一来源为用户级 AGENTS「任务完成：本地业务保真与技术自主收尾」。通用执行方法在现有 git-task-lifecycle Skill；本文件仅维护装点猫的实际入口、保护能力和部署条件。

## 入口与完整快照

收到用户本人“任务完成”后，首先在登记的实际开发 Worktree 执行 `npm run task:completion -- begin`。也可使用 `npm run task:completion -- freeze` 单独接受；首次 deliver 在任何补修前也会冻结。不能在补修后重新接受业务。基准由隔离 Git index 捕获完整本地源码（含已检查的未完成内容、未暂存/新增文件和删除），不会更改 HEAD、用户 index 或工作文件；捕获期间源码移动会阻断。私密输入不得进入源码，忽略的运行资产仍按原资产规则保留。

接受结果写入 Git 内容寻址对象、`refs/zdm/accepted/<batch>` 和 Git common dir 内只创建一次的 `task-delivery/<batch>/accepted-source.json`。业务内容按路径、mode 与 blob 对象核对。恢复和重复指令复用原基准；不能以新候选覆盖基准。工作区里后来出现的业务修改不会进入旧候选，原工作区不满足干净条件时不能清理。

`npm run task:completion -- check-source <40位候选SHA>` 验证候选。begin/freeze 接受不等于提交或推送；仍按现有模块检查点和正常 Git 提交保存，保留模块历史与用户新增工作，不自动把开发状态改成完成。已检查的半成品与工程交付就绪分开表述；原模块就绪、检查点及依赖门禁保留，暂停/排除冲突不靠快照自动解除。快照提交同时保存接收时的模块开发状态及依赖；验证通过后可按原入口登记工程交付就绪，这不表示半成品业务已开发完毕，也不覆盖接收时的开发状态。未通过门禁不能登记就绪。

## 保护范围与技术自主

策略唯一来源为 `scripts/accepted-source-policy.mjs`，它自身、校验器、用户授权入口及本文属于冻结控制面。其余未分类内容默认保护；src、生产后端、迁移、UI规则、package及锁文件、生产构建配置不因技术修复被放行。混合文件没有字段级适配时整体冻结，不用正则猜测业务片段。

已存在的工程脚本、测试、测试后端、CI和工程说明采用预定义技术范围。新文件仅保留原技术范围内预先审查的测试、`scripts/delivery-repairs/`、`ci/test-fixtures/` 和工程说明入口；新未知脚本、工作流或配置默认保护，不允许候选扩张策略来放行自己。技术用途还须查清真实消费者，生产用途不能因目录名被当作技术修复。

冻结后 pre-commit 对待提交 Git tree 校验业务内容，运行原 ESLint/Prettier的只读版本，不再用 --fix/--write 改写验收源码；普通未冻结开发继续原 lint-staged。钩子可被本机账号绕过，不能作为远程强制保护的替代。

旧测试按已验收业务适配，确已废止的测试可删除/替换；不要求历史测试数量永久不下降。失败本身不代表测试失效，不伪造结果或移除有效验证。测试/CI、直接必要登记、Git和交付工具技术故障无需另问，但保护机制本身不属于普通收尾补修授权。

## 推送与合并校验

交付入口在准备、候选及最终main上校验冻结业务。接受 commit 发布为 `refs/tags/zdm-accepted/<任务分支slug>`；同一基准只允许首次正常创建和同值复用，远端存在不同值时拒绝，不强推。标签是审计基准，不在任务分支清理范围内。

原任务分支可以正常快进推送必要技术补修；真实远端分叉仍阻断，不通过覆盖远端解决。main整体技术树可随正常合并变化，最终准确main CI必须验证实际结果；业务与控制面必须匹配原快照及明确受信主线的合法组合。合并前要求准确main是候选祖先，并核对实际merge tree；配合服务端strict最新主线保护阻止检查后的主线并发推进。远端业务变更冲突由校验阻止，不自动混入或改写验收版本。

## 并行任务的主线组合

v2接受对象额外固定原任务base、冻结时origin/main及二者与任务的实际integrationBase；不重建v1原始树、业务摘要或接受ref。原任务delta以冻结时integrationBase为准，与最新受信main按Git三方组合；显式比较任务业务、主线成果、删除和冻结控制面，冲突或任务成果被主线覆盖时阻断，不自动解冲突。旧冻结缺少这些原始输入时保持原恢复规则，不事后推断升级。

本地组合证明记录接受对象、准确main、旧任务HEAD和真实候选merge tree；先停当前任务监视器，再合并并登记自身merge提交。中断只恢复该原意图，不重置工作区。main合并顺序由交付队列保护，变化后的准确候选必须重新检查。

可信远端只接受GitHub事件的准确base SHA；从该受信checkout独立计算候选实际PR merge tree及原冻结加main的预期树，不信候选提交的本地composition.json或自选主线。仍不执行候选代码；来源控制面调整仅由本次已获明确授权的工程改造实施。

## 可信基线校验与部署界限

`.github/workflows/accepted-source.yml` 使用 pull_request_target，检出准确 base SHA 的可信工具，仅 fetch 候选和接受标签的 Git 对象；不检出、不执行、不安装候选代码。校验分支与批次绑定、接受 commit parent、业务和控制面的完整清单后，向准确 PR head 发布 `Accepted business snapshot` 检查。

本工作流使用 GitHub Actions 共享身份，**单独启用不等于不可绕过**：具有相同检查发布能力的其他工作流可能伪造同名检查，管理员也可能修改保护。强制防绕过必须另具备：

1. 接受标签 update/deletion 规则生效，无日常执行者绕过权限，匹配 `refs/tags/zdm-accepted/**`。
2. main 强制最新候选检查、管理员受保护、禁止强推删除，并强制接受快照检查。
3. 检查绑定独立 GitHub App/可信执行服务，发布凭证不暴露给候选及日常执行账号；仅同名 Actions 检查不够。
4. 日常执行身份没有修改上述保护、改写接受基准或管理独立发布者的权限。
5. 可信策略与校验代码不由候选替换；保护机制更新走用户单独批准的维护批次。

先发布可信工具，再由有权维护者启用上述保护，避免要求一个尚未发布的检查导致部署自锁。首次部署沿用现有受保护质量流程，必须如实标注独立保护未启用，不伪造已具备的能力。实施任务的“执行”不替代正式推送/合并的“任务完成”授权。

`node scripts/accepted-source-readiness.mjs` 只读检查实际账号、main保护、接受标签规则和可信工作流发布；缺失返回2并列出事实。它不创建凭证、不改变角色或关闭保护。检查绑定还须由维护者证明发布凭证隔离，结构配置通过仅显示configurationReady；本工具无法独立证明发布凭证隔离，因此仍保留independentEnforcement=false和非零退出，不以配置就绪替换成功条件。独立权限演练与受信证明未落地前，不能报告独立强制保护已生效。

当前实施前核查：日常身份 ADMIN；main 仅 Frontend quality/Backend quality；无标签规则集。故本次只能先交付内容校验与可信工作流实现，**不能宣称已完成独立账号、物理只读隔离或远程防绕过启用**。本地 Git ref/400文件权限不构成对同一OS账号的独立安全边界。

## 验证与回执

使用隔离 Git 仓库演练无人回复、未提交新增/删除、技术补修、业务增删改/改名/mode、基准篡改、控制策略修改、分支绑定错误、重复接受/发布、远端基准不同值、远端快进/分叉，以及最终main与快照一致。保留原门禁、首次失败、运行交接与资产保护测试。

结果分别记录本地快照检查、可信基线工作流是否发布、标签保护、独立发布者及日常权限隔离；任何一项未证实，不报告“不可绕过”。实际无法继续时尽可能保存成果并明确区分保存、合并、交接和完整交付，不无限等待常规技术确认，不改业务或编造耗时。

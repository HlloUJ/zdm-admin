# 任务中断发现与安全续接（284）

本任务复用现有任务登记、completion journal、921通知传输及原正式恢复入口，不新增执行器，不修改原任务锁或失败证据。

## 有限验收边界

1. 已记录阶段的执行者消失，显示中断，不继续显示已证明执行中、不推断成功。
2. 有失败回执但没有后续阶段（例如756 prepare失败后长期空档），显示受阻并通知负责接续的人。
3. 显式暂停、身份不明、PID复用/权限不足、缺失记录均不能自动恢复。
4. 受控续接必须核实授权、候选、原执行者、完整资源及上一步外部副作用；经原执行器在自己的队列/锁内再次验证才能启动。持久claim先于启动，重复调用、进程重启及未知结果不得重放。
5. Mac通知复用921传输，操作系统接受不等于用户看见；提交结果未知不盲目重发。
6. 检查器退出/重启后保留原任务及续接claim。计算机关机时不运行；登录启动机制与真实重启验收尚待发布接入，不能声称完成。

## 当前实现状态

- `node scripts/task-continuity-cli.mjs --once`：只读采集，写本任务私有最新快照。
- `--watch`：每分钟重新读取真实登记/阶段和探测owner，不从旧看板猜测运行状态；进程退出即停止，尚非已安装常驻服务。
- `--notify`：显式使用Mac通知；不向在线任务总览写入或保存用户可见历史。
- `continueVerifiedTask` 是受控编排接口，不提供任意命令回放。已增加严格限于已存在PR CI等待的原入口适配器；其他正式交付阶段及921接入尚未完成，默认不启用自动续接。
- 当前登记只有PID的旧记录不能证明进程身份，故报告`unverified-running`，而不是声称运行中；无completion记录的开发任务报告`unobserved`，不能据此判断停止。

## 不包含

不重建数据库、不切换5179、不终止其他任务、不清理未知锁、不改GitHub保护、不把失败重标成功。资源等待恢复继续由921负责。正式交付沿用受保护工具；适配证明不足时先通知并保留现场。发布后才接入真实持续监督及状态映射，候选代码不能冒充已发布入口。

## 根线程接手契约

本地代码不能唤醒云端agent。根线程提供实际任务→worker映射后，通过`continuityHandoffs`产生事件；不得从Git owner UUID猜worker。每条事件含稳定任务ID、准确worker、原owner、授权来源和原始观察。未映射/观察超过两分钟不能发送续接。

根线程先读取原worker状态；运行中只传信息，不启动第二个执行者；空闲且授权范围一致才用原worker的follow-up入口。`claimContinuityHandoff`在发送前独占持久claim。发送结果不明须读回原worker，不自动重发；`receiptContinuityHandoff`记录读回依据，发送成功不能标为任务执行成功。新阶段产生新事件，同一观察不反复唤醒。

验证器的旧running汇总单独附带`recorded-running-unverified`与原attempt/candidate指纹，绝不从旧状态猜定已中断。原worker核对完整资源/首次失败，使用原验证器恢复规则，观察器不动锁。

当前只完成接口与隔离测试，尚未接入根线程automation，不声称已可持续唤醒或重启续接。Mac启动与云端可达性验证等待根线程安排受控场景；不能为测试重启用户电脑。

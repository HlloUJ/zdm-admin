# 统一交付标准的工程映射

规范来源：[统一交付与验证标准 V1](https://app.notion.com/p/41a572fed032818fbae3eb9c2874092b)。执行配置为 `ci/delivery-standard.json`；本页只说明映射，不维护第二份分类算法。

## 计划、阶段和证据

`delivery-standard.mjs` 读取版本化配置，按最高风险和全部匹配要求的并集生成计划。普通源码路径、共享调用路径、敏感路径、执行规则文档及未知输入分别分类；局部样式不能覆盖共享规则；只有明确CSS源与完整已知样式消费者、实际Vite+Vue scoped @import编译契约可证明时，才排除路径业务关键词误判。全局/共享样式至少R3，raw、动态或未证明消费保持未知R4。实际完整回退若源于未知传递影响，计划明确记录scopeUncertainty，不能仅因泛路径匹配声称范围已知。路径分类只是保守下限，不能证明业务语义、异步等特征不存在；现有业务契约、反向使用方和工程输入证明继续决定实际检查域，无法证明则保守完整回退。

| 标准职责              | 执行入口                                                   | 结果与保护                                                                                             |
| --------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| R0–R4、未知与混合改动 | `delivery-standard.mjs`、`verification-impact.mjs`         | 版本、配置摘要、规则、要求并集、保守影响域                                                             |
| 本地实际验证计划      | `verify.mjs`                                               | `.task-verification/plans/<digest>.json` 绑定源码内容、基线、平台与实际命令；不是检查通过证明          |
| CI适用域与计划核验    | `ci-quality-evidence.mjs` 的 scope/verifyScope             | 重新计算完整计划；旧配置、缺失计划和篡改均拒绝，不重解释历史报告                                       |
| 本地/PR/main分工      | `verification-policy.mjs`、既有 CI 与 `ci-equivalence.mjs` | 可靠CI承担最终候选适用门禁；高风险本地缺口不取消；main只使用已证明等价的原始完整报告                   |
| CI能力回退诊断        | `deliveryCiCapability`                                     | 记录 repository-identity/main-protection/quality-workflow 失败阶段；不保存潜在凭证错误正文，不削弱回退 |
| 执行/复用/失败        | 既有 verification-runner 与 performance                    | 保留首次失败、精确输入、实际环境、复用拒绝原因及执行墙钟                                               |
| 中断接续              | 既有 completion-session/flow                               | 只接续未完成或证据失效阶段；控制入口使用main锚点，不依赖待删除工作区                                   |
| 清理移交              | `build-task-app.mjs`、`task-cleanup-handoff.mjs`           | 创建时证明、稳定载体、持久化清单；定时消费由独立清理入口承担                                           |

计划不自动授权排除检查，不把风险等级当作执行成功。现有前后端必需汇总、来源冻结、首次CI、零跳过/零重试、运行交接均保留。现有分类器已经支持可靠CI轻量就绪，不能把历史耗时直接当作“无条件本地全套”的证据；优化需按本次回退与复用拒绝原因定位。

## 清理生产与生命周期接口

真实 Vite 成功构建、构建前后源码一致的任务专属 `dist`，以及创建时登记的 E2E 构建、Git 模板夹具、准确 Git 源码副本，按独立证明类型移交。无创建登记、旧输出、修改过的输出、依赖树、必要失败日志、原始报告、数据及备份继续保护保全，不凭目录名或年龄推断。`node_modules` 含软链接和潜在唯一内容，不能借本方案擅自清理。

构建 wrapper 不改变Vite参数或退出码。仅有准确 task-artifacts 登记时生成 `.task-runtime/cleanup-dist.json`。移交前核对源码摘要、对象身份及现有运行/预览引用保护；main CI、运行交接和正式来源检查仍由 settle 的前置步骤承担。

移交先持久化不可变重建证据与意图，再把同一文件系统的对象移到：

`git-common-dir/task-cleanup/staging/<永久任务ID>/<对象ID>/content`

原始 manifest 使用0600、wx；载体及目录0700。manifest v1固定 producer `task-completion-handoff-v1`，包含task、carrier、path、identity、proof、disposition、notBefore。`proof`绑定worktree、head、accepted、main及rebuild；rebuild指向稳定proof原始字节和SHA256，不是任意safe布尔。

`task-cleanup-queue.mjs` 为任务683提供的唯一消费者；生产端调用其 cleanupIdentity、cleanupObjectId 和 createCleanupQueue.handoff，不实现第二套身份算法。部署依赖顺序必须先具备该消费者，再启用新的构建登记入口。移交失败保留对象/意图并阻断收尾，不冒称已释放空间；消费者只在正式closeout及main读回通过、无引用且身份未变后删除。详细记录保留期和容量未获确认时不自动删除记录。

## 指定任务恢复与执行者观察

全局暂停时，`resume-selected` 仅恢复明确成员的开发准入，保留既有交付单例、其他票据状态及原收件顺序。准入要求真实原生用户请求身份、原owner/room、登记与监测上下文，以及一致的实际容量快照，始终预留一个交付位。未知容量、遗漏正在交付的占位、重复成员、跨owner、交付成员均拒绝。不得用本候选手改真实队列或把未发布能力称为已发布。

同一个原生聊天下的 collaboration 子执行者必须以真实canonical身份观察。父聊天活跃或最新一个command.cwd不能证明每个子执行者活跃；缺少canonical执行者观测适配时应为unknown，不能编造native threadId、套用Dot路径或自动释放/恢复。候选提供显式 `collaboration-agent` 登记和注入式 `readAgent` 接口；直接观测必须同时绑定canonical、准确task/owner/worktree及新鲜宿主快照。实时宿主尚未接线时保持unknown，不宣称已完成平台观察部署或独立权限隔离。

工程类型成员在明确恢复时同时绑定原恢复消息、永久任务ID、owner和工程kind。开发完成后，`execution-order promote-delivery` 读取准确registry并复核原开发报告、干净HEAD及其completion摘要，再用原授权引用创建派生交付准入；它不伪造另一条用户消息、不更新时间、不把原source重放成任意动作。新的pause会撤销尚未派生的资格，业务任务及缺证明任务拒绝。

派生仍须依赖准入和既定顺序，交付单独持位；已有交付或受阻持位不会被抢占，其他开发例外保留。重复派生只读回原票据，不旋转admission、不恢复blocked、不再次执行验证；最终main队列与共享资源互斥继续由原执行器承担。当前bootstrap载体仍须经已发布受理入口安排，不提供泛化adopt或直接import registry的绕过路径。

## 最低要求的实际生产者与通过证明

`coverage.requirements` 和 `coverage.specialties` 将每条要求绑定准确producer，`coverage.engineeringScenarios`登记工程专项的准确文件/用例名。配置及执行输入相同，生成相同obligations；生成时一律标记 `planned-pending-evidence`。未知要求、缺producer、错误命令/阶段、缺R4专项映射均成为gap，并在昂贵门禁前拒绝。等级标签不能证明执行通过。

| 要求                         | 实际执行/证据                                                                                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| diff、R0文档契约             | `delivery-input-contracts.mjs`实际运行Git diff检查；只核对本次变更Markdown的内部文件引用及冲突标记，忽略代码示例、外网链接和历史未改文档；报告绑定候选、基线、完整变更集合和标准摘要 |
| 格式                         | 原formatting phase的准确命令和成功metadata；不得用风险标签或其他命令替代                                                                                                             |
| 静态                         | 工程使用原light-checks；前端使用原quality:static；后端使用原Maven质量链                                                                                                              |
| 单元、流程、边界、共享使用方 | 根据实际影响域，使用原工程全集/前端单元及完整首过分片/后端全集；原适用清单、项目业务契约和完整报告校验继续承担范围证明                                                               |
| R1交互/视口                  | 既有适用自动化完整列表与无重复、无重试分片并集，不新增人工浏览器验收；新增行为仍须按原业务覆盖契约维护真实用例                                                                       |
| R4工程专项                   | 在原完整工程报告中要求准确的允许/拒绝、失效及恢复场景；缺失、改名、失败、跳过或重试均不能满足要求                                                                                    |

CI前端/后端原聚合分别核验自己的obligations，标记 `partial-satisfied`；收尾证据核验复核两域及共同证据后才能得到完整 `satisfied`。共享证据不启动第二遍测试；新增的是轻量契约检查和原报告消费。正文业务含义及新增行为的正常自检、原来源保护和用例覆盖责任不被路径分类替代。

当前全局暂停的恢复例外只允许一个准确交付scope；正常未暂停时仍使用实际state.limits及最新项目双FIFO规则，最终main/共享资源互斥继续保留。不把历史V1的交付描述改写成当前全局worker上限；旧宿主capacity helper与最新试行规则的差异尚不能据此宣称全部调度策略一致。

## 收尾总清单覆盖矩阵

除可消费dist清单外，`recordCloseoutCleanupInventory` 复用创建时task-artifacts及已有preserveAssets清单，持久记录所有已知资源的分类、原因和稳定保全引用。既有清单只在当前任务内读取，不扫描其他任务或未知历史临时目录。总清单写入失败仍是移交失败；保护条目不是删除许可。

| 类型                             | 当前处理                                                                              | 明确边界/缺口                                                                  |
| -------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 未变化且有创建证明的dist         | 稳定载体、不可变manifest及消费队列                                                    | 仅正式closeout/引用/身份核验后可删除                                           |
| 私有依赖、外部依赖链接           | 现有完整保全并登记准确归属/位置                                                       | 不放开软链接或共享依赖保护，不把无重建证明当无用文件                           |
| 依赖缓存、安装备份               | 保护保留                                                                              | 不因本轮清理扩大既有删除授权                                                   |
| 测试临时输出/夹具                | 创建时证明的 E2E 构建和 Git 模板夹具自动移交                                          | 未登记、修改过或唯一内容保留，不凭目录名采纳                                   |
| 临时源码副本                     | creator 索引绑定完整 Git 输入及文件集合，外部稳定载体纳入总清单                       | 不扫描历史临时目录或其他任务，额外唯一文件保护保留                             |
| 必要原始报告、首次失败、运行证明 | 保护保留，引用既有内容寻址清单                                                        | 不能以到期/重复名义丢弃必要证据                                                |
| 冗余报告副本                     | 仅test-results/playwright-report/coverage完整额外原副本逐字节证明已保全后移交稳定队列 | 正式closed后才消费；必要原始blob、首次失败与.task-verification不删，缺证明保留 |
| 其他已保全任务输出               | 待核查                                                                                | 不能由目录名推断可重建或清理                                                   |

总清单区分能力覆盖、已接受移交与保护/待核查对象。存在未分类资源或缺创建登记时，`implementationComplete:false` 并列出原因；能力已实现不表示所有旧资产可删，也不表示已释放空间。683 的运行 policy、真实日程和通知仍须完成实际验证。

## 实时进展与过期事实

实时交付使用[稳定回执宿主](completion-progress-host.md)，原417协议和十分钟兜底通道不另建；有界阶段前drain避免同步长命令延迟started。正式流转由准确冻结/准入和正式deliveryStatus证据产生，失败不假报完成。

已发布v35缺retryable字段的过期事实按[过期回执隔离](stale-progress-receipt-recovery.md)分开保存真实服务器拒绝、旧客户端拒绝记录和从未提交的已取代事实；不改原包、不假ack、不删除首次失败。真实历史恢复由总协调在发布后完成，源码隔离测试不当作生产送达证明。

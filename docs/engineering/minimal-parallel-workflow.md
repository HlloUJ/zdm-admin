# 最小并行开发流程

各任务按需创建独立分支和永久 Worktree，依赖、缓存、构建与测试报告各自保存。任务数量没有固定为两个；前端端口池为5177至5199，独立后端端口池为8081至8099，同时运行数量受端口与机器容量约束。首次验收至少使用两个任务，不能把两个验收任务解释为产品上限。

## 日常入口

从干净的已发布 main 锚点使用现有 `task:entry`。先核实登记与真实会话 owner，再创建或恢复准确任务。启动登记仍不切换预览。

```bash
npm run task:entry -- registry list --json
npm run task:entry -- start --slug <task-id> --kind business
npm run task:entry -- --worktree <exact-task-directory> preview start --task <task-id>
npm run task:entry -- --worktree <exact-task-directory> preview status --task <task-id>
npm run task:entry -- --worktree <exact-task-directory> preview stop --task <task-id>
```

尖括号内容必须替换为实际登记身份，不是可原样运行的示例。命令执行器必须能够写入项目 Git 登记、访问 Docker 并监听本机端口。系统终端没有原生会话环境时，使用实际已经核实的 `--owner`，不编造身份。

`preview start` 复用原前台启动器，保持在该任务的执行会话运行，不新增守护服务或另一个后台调度器。它返回并输出当前任务自己的预览地址；各任务可同时访问。已有健康预览会先核验再复用，无法核验时保留现场。Ctrl+C沿用底层规则只关闭前端并保留后端；需要完整停止任务运行资源时使用准确的 `preview stop --task`。

`preview status --task` 检查端口归属、Worktree、分支、运行 nonce、API代理及已登记数据绑定。必须明确返回 `runtimeReady: true` 才能判定运行就绪；`not-previewing`、`unhealthy` 或 `runtimeReady: false` 都不通过，即使命令退出码为0。运行就绪不等于业务质量通过，结果明确保留 `verificationProven: false`。独立任务的适配检查入口使用 `preview check --task <task-id>`：复用上述只读查询并强制要求 `runtimeReady: true`，否则返回非零，不启动或重启任务。适配检查不使用默认指向兼容5175的裸 `check`；只有定向诊断时使用 `check --port <该任务实际端口>`，不得猜测或固定其他任务的端口。不带任务的历史 status、显式 switch 与已有5175保留兼容，普通任务无需抢占它们。

只有 start 接受可选 `--port 5177至5199`、`--backend-port 8081至8099`；默认按现有端口池分配。固定5173、5174、5175、5176不属于独立任务分配范围。端口不足时报告错误，不停用其他任务腾位置。

## 数据准备

默认采用保守的独立全栈路径。新任务的隔离数据登记缺失时，start 作为已经授权的高层协调入口，先调用现有显式 isolate 准备步骤，再调用底层启动器；底层启动器仍拒绝缺失数据。准备沿用既有归属、锁、备份、复制校验及媒体隔离，不连接集成资产作为任务运行目标。

已有数据登记复用前仍验证实际数据库及媒体卷。损坏登记、初始化中断、数据更新中断、已登记但消失的库或卷都保留并报错，不自动重建。历史部分恢复、原共享数据任务和已经冻结的交付候选不能通过普通 start/stop 改写保护状态。

纯前端任务只有在稳定后端及共享数据互不影响得到实际证明时才可以复用；现有显式 frontend/API 调试入口保留，但新的日常入口在缺乏这份证明时使用独立环境，不自动接入另一个未完成任务的后端。数据库服务实例可以复用，独立逻辑库和媒体空间按需要分配。

## 质量与交付

已有UI视觉规范、公共组件、权限和数据规则、有效业务测试、源码守卫、CI必需门禁及原冻结保护继续有效。工作方式适配只修改必要入口与工程测试，不能放宽断言、减少必要覆盖、跳过或重试测试来报告成功。

各任务在自己的工作区修改与验证，按准确候选保存证据。没有业务依赖时，B可在A未完成时单独交付；主线合并、集成资源变更和正式运行交接继续使用原受保护队列，不另建交付系统。实际交付前停止本任务监视器，保留其他任务前端及后端引用保护。

已批准的Flyway迁移随代码进入准确交付版本，在集成库和已发布预览库分别实际执行并验证；不复制任务测试订单等临时数据，不自动修改其他未完成任务的库，不扩大生产发布与数据删除授权。

## 最低验收

| 项目         | 必须证明的结果                                                            |
| ------------ | ------------------------------------------------------------------------- |
| 实际执行权限 | 同一日常执行通道可创建/提交任务、访问Docker、安装依赖、监听和停止所属服务 |
| 多任务创建   | A、B独立登记和依赖；再创建任务不需要改变流程；不抢占旧预览                |
| 独立预览     | A、B各自URL绑定正确源码、API、数据库与媒体                                |
| 故障隔离     | A的源码/API失败不影响B；状态不把未知或错误身份报告为健康                  |
| 停止与恢复   | 停止A保留B及全部数据；A恢复复用原数据；陈旧nonce拒绝停止新运行            |
| 失败保全     | 权限、占用端口、坏登记、初始化中断和外部API消费者均准确报错并保留现场     |
| 原质量门禁   | 所有适用原门禁仍实际生效，逐用例证明零跳过零重试                          |
| 独立交付     | A未完成时B通过原PR/main门禁及运行交接，A源码、登记和环境保持正确归属      |

单元或模拟依赖测试不能代替Docker、真实双任务运行和正式交付证据。每项区分通过、失败与未运行；任一必要项缺失时，只报告实际阶段，不能宣布整套流程正常可用。

## 保全与切换

现有任务、未提交成果、原冻结、历史失败证据、数据库、媒体及备份保留。候选入口必须完成验证并受信发布后才作为日常入口；不通过复制候选到main冒充已发布能力。无法完成切换时继续保留原归属，禁止通过删锁、强制重置、删除旧任务或重建数据解决。

## 原生隔离核验

真实验收应使用各任务的实际数据库账号连接，核验只能访问自身逻辑库，无法访问另一任务或集成库；同时核对独立媒体卷。停止与恢复后保留数据绑定，并验证旧运行 nonce 无法停止新实例。

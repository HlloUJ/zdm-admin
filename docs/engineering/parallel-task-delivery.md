# 并行独立任务开发与逐任务交付——唯一实施标准

状态：用户已于2026-11-08确认实施。本文替代此前“共享一个开发分支、多个窗口并行写入、统一批次交付”的改造方案。历史备份、失败记录及冻结回执仅作保全证据，不作为另一执行标准。

## 不变边界

- 多任务同时开发，各任务独立分支、Worktree、暂存及可写产物；每完成一个独立任务可正式交付一个。
- 5173保留已交付组合，5175保留明确选中任务，额外环境按需；不默认每任务一套常驻全栈。
- 确认/执行进入实施、自检、反向审查、修正、回归闭环；任务完成才授权当前准确业务任务正式交付。
- 正式主线合并与运行交接串行，开发目录不因此被全局锁住；main合并不等于生产发布。
- 不改两个未完成业务任务的产品语义；不擅自合并、重置、变基、强推、删除、stash或清理数据。
- 原始冻结快照不可重建；源校验保护不可为候选自行放宽；main组合须追溯独立受信输入。
- 旧脚本兼容必须经证明，未知归属安全拒绝；不把方案中拟新增命令当作现有能力。
- 唯一进度记录为固定项目目录下的 `.task-runtime/preview-recovery/parallel-task-delivery-progress.json`；它独立于待清理的工程Worktree，属于现场执行记录。完成数以证据为准，编号按下列步骤，不把执行中标作完成。
- 既有改造记录由该追踪接管；先前已通过的证据只有经输入/环境/产物等价验证后才复用。

## 当前必须保留的事实

当前已安装的停止归属和失败保全保护保留；04f4c6c候选及原失败日志保留。operation-feedback-standard为未完整交付的旧冻结身份，payment-config-cleanup为当前预览选择。两聊天归属已经通过各自实际恢复报告及原生会话身份核实：“讨论订单需求”对应 payment-config-cleanup；“梳理商品中心页面化方案”对应已失效的 selection-center-prd 临时目录，拟仅将已证明的13份历史实施文件放入永久 selection-center-recovery 目录。后者仍是部分恢复，不能视为最终工作区或开发完成；实际登记迁移与会话采用须另有现场回执。

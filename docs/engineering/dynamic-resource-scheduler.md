# 动态资源调度（任务 921）

## 目标与边界

默认利用可用资源并行推进独立任务，出现资源压力时减少运行组，资源稳定恢复后自动重新推进因资源暂停的阶段。保留原测试、零跳过、失败诊断与证据要求，不通过弱化质量提速。保留 main、固定 5179、共享后端/数据库、用户 Chrome 和其他任务的运行身份。

现有 resource-lease 解决归属互斥，delivery queue 解决主线交付顺序，二者不是性能调度器。e2e-resources 仅提供可选 Linux /proc 观察。新机制不替代这些安全约束。

## 实现形态

项目 Node 脚本，不需安装第三方监控软件。后续常驻部署复用 macOS launchd。Skill 可说明任务登记入口，但不能替代实际采样、状态保存与进程控制。

当前候选已实现：纯调度决策状态机、独占生命周期锁和原子持久状态、Mac/Docker 只读采样、持久待送达事件模型、模拟测试。**尚未接入运行执行器、常驻服务和用户通知桥接，未接管任务，不能宣称自动暂停/恢复已启用。**

## 调度决策

- 同一仓库单调度器独占锁，工作组有不可复用的 job id、任务编号、阶段、工作目录、准确输入指纹、峰值资源预算、互斥资源、是否可安全中断。
- 初始上限 4 组，其中最多 2 个 Docker 重组；上限只是保险，不预留固定闲置。按真实预算、资源互斥和依赖计算能开几组，不把所有测试强制串行。
- 5 秒采样；Mac 与 Docker VM 的预算分别核对。保留 Mac 2 GiB、Docker VM 2 GiB、磁盘 10 GiB 的余量；Docker 配额不是 Mac 剩余内存。
- CPU 忙碌达 85%、内存压力、交换增长或 IO 拥塞时停止准入；压力持续 15 秒时请求减少一组。Docker 可用低于 1 GiB 时立即请求减少一组。
- CPU 降到 70% 以下且全部指标恢复连续 60 秒后逐次准入。未知、过期或失败读数不能视为资源充足。
- 计入已运行组的完整峰值预算，避免新启动尚未到峰值时过量准入；此做法偏保守，之后仅凭测量校准。

阈值为待真实运行验收的初始保守值，不是已证实最优参数。Mac memory_pressure 的 free percentage 只能作为可用内存估算，非空闲页精确字节。采样器保留原始含义，后续需连续样本计算 swap 增量并校准 IO/内存压力信号；不能拿单次快照直接宣布稳定。

## 暂停、恢复和证据

优先在阶段边界停止准入。需要主动减少占用时，只允许对调度器自行启动且身份核对正确、声明可安全重跑的阶段发送 SIGTERM；不使用 SIGSTOP，不全局结束 Chrome/java/Docker。实际子进程/容器控制适配必须核对 run token、PID 启动时间、专属进程组/容器标签，终止后验证已结束才进入“资源暂停”。无法证明归属、无法退出或共享服务异常，保留现场并阻塞，不擅自杀进程。

恢复不是从测试内部断点继续，而是仅重跑被中断的完整阶段。已完成的有效阶段证据保留，只有对应输入、依赖和环境指纹仍匹配才允许复用。普通测试失败、权限失败、证据缺失不得自动无限重试。最多 3 次资源中断后转诊断阻塞并通知。

重启恢复必须检查锁归属、记录进程是否真的结束及源码指纹；未证明时不重复启动。当前存储锁对异常退出 fail-closed，自动安全回收尚需运行身份适配验证。Mac 关机、休眠、离线时不能保证持续运行，唤醒/联网后恢复仍需验证。

## 主动通知

每次安排调整保存有序 outbox 事件：涉及任务、阶段、原/新状态、原因、时间。发送成功获得用户会话的真实 message id 后才标为已送达；本地日志不算送达。相邻内部 start/running 事件由桥接聚合为一次实际安排通知，不重复轰炸。发送失败保留待送达，有限退避重试；任务状态与通知送达状态分别展示。

必须接入可唤醒 root 或用户可达的受支持通知链路，并实测暂停、恢复和发送失败后的补发。不将本地脚本伪装成有聊天发信权限的服务。当前 outbox 模型已测试，真实送达未测试。

## 启用前剩余验收

1. 将现有验证器按可中断阶段登记；保留现有 lease/资源隔离和证据输入，不接管已运行中的组。
2. 完成执行器：源码校验、持久化启动意图、准确身份回执、容器/子进程归属和安全停止。
3. 实测双采样、健康/压力映射，确保共享 5179 和后端不受影响。
4. 在独立轻量假任务验证压力暂停、稳定恢复、失败不重试、旧 PID/变更源码阻断、崩溃窗口恢复。
5. 验证用户通知桥接送达，断开时保留事件且恢复后补发。
6. 与主协调者协商安装用户级常驻服务后，验证退出重启、睡眠唤醒和正常卸载。未部署前保持人工协调。

## 第二阶段候选：运行控制与门禁准入适配

新增 `task-resource-runner.mjs`，仅控制本次调度进程亲自创建的 detached 子进程组：先持久化启动意图，再启动，记录 PID/PGID/启动时间/run token；停止时逐项比对，只发送一次 SIGTERM。未知或已退出的 leader、重用 PID、外部容器、不可重跑阶段均拒绝。启动后存储失败保留控制器现场，不隐去可能存活的进程；日志写入失败不得报告成功。没有自动认领旧 PID 的入口，也没有自动清除旧证据锁。

新增 `task-resource-verification.mjs`，通过现有 `executeVerificationPlan` 的 `run` 注入点做阶段准入，不修改默认门禁。等待准入后再次校验输入指纹和命令/环境摘要，然后调用原 `runVerificationTask`，原任务参数、覆盖、报告校验、有效复用及首次失败历史保持不变。

两种暂停明确分开：

- **阶段边界暂停**：既有后端/浏览器门禁默认属于此类。已开始阶段正常结束，新的阶段暂不准入；资源稳定后恢复排队阶段。不承诺立即降低已运行阶段的占用。
- **受控中断重跑**：仅用于显式声明可重跑、没有外部容器生命周期、属于本调度器的独立进程组。需实测终止整个所属组，结束后才能重新排队。Docker/浏览器旧门禁不自动进入此类。

本轮运行控制与准入接口用模拟子进程、模拟准入服务独立验证；没有运行真实重测、真实发信、常驻安装或重启。当前尚缺实际队列 broker/常驻协调循环、旧门禁合作式中断和用户通知唤醒桥接，不把可测试接口称为已部署能力。

通知能力已核查：当前工具的 webhook 仅提供指定在线连接器事件，没有本地状态文件变更触发器。Node 脚本没有用户会话发信权限。可由 root 使用支持的持久自动化读取 outbox、发送后写入真实消息回执，但该链路尚未建立和实测；不能用日志、模拟 send 或定时器代替真实到达。是否能提供事件级及时通知仍有平台能力待确认。

## 第三阶段候选：实际持久准入协调器

`task-resource-broker.mjs` 已将调度状态机、持久存储和原门禁准入接口连接起来；调用方提供经审查的峰值预算与原验证证据校验，不内置猜测预算。调度决定成功落盘后才向等待者发准入凭据；写入失败立即停止准入，不假装任务已启动。

当前提供单进程协调 API，仍没有对外 socket/HTTP 服务，也没有安装调度循环。旧进程异常若不能证明所属工作已结束，标记运行状态不确定，保留资源保护并阻断新准入。重启发现未核实的活跃阶段时拒绝启动调度，不能将“进程离线”直接当成“资源已释放”；原门禁锁、容器和失败历史保留。普通已结束的失败阶段明确阻塞但不无限重试。

测试已覆盖原准入适配调用真实 broker、磁盘状态存储往返、准入前写入失败、同目录互斥、无主排队、旧活跃状态恢复阻断、通知回执持久保留。门禁命令仍用假执行函数，通知回执仍用测试数据，不能作为真实执行或用户送达证据。

## 第四阶段候选：跨进程服务与串行采样循环

新增 `task-resource-service.mjs`：只在调用方明确启动时监听私有 Unix socket，不监听 TCP，不安装 LaunchAgent，不寻找或接管现有任务。目录必须为私有权限，socket 为 0600，调用必须持有独立能力令牌。现有 socket 占用时拒绝启动，不删除旧端点。协议只暴露准入/状态/回执方法，不提供任意 shell 命令执行接口。

准入、完成、阻塞及通知 ack 使用请求 ID 和输入摘要持久去重。先保存待处理意图，再执行操作，最后保存结果回执；客户端丢失响应时使用原请求 ID，不另建一份任务。若服务崩溃在“动作可能已经发生、结果尚未落盘”的窗口，重启拒绝重放，必须查明实际效果；不能把“不知道”当成“未发生”。已确认完成的请求在重启后直接返回原结果。等待准入的响应在当前进程内复用，不重新注册第二个执行者。

串行采样循环逐次 await 完成后再等待下一次，不允许采样/调度重叠；读数调用或协调器失败时停止并保留现场，未实现有限恢复策略之前不暗中无限重试。循环与实际采样政策转换、任务接入、服务启动配置仍需最终组合验证，目前没有常驻运行。

已做隔离跨进程 Unix socket 实测（第二个 Node 进程只查询假状态）、能力令牌拒绝、重复请求、持久回执重新打开、崩溃窗口阻断及串行循环测试。测试临时端点退出后清理，无真实门禁、容器、浏览器或数据库被操作。安全阻断的重启恢复不等于所有故障均能无人值守恢复。

用户可达通知仍是独立阻碍：socket 是本机工程进程间通信，不是到 dot root 的通知通道，不据此声称已完成主动告知。

## 当前已选通知方案 A：本机通知 + 看板留痕

用户最新选择替代前述 root 实时通知设想：使用 Mac 原生通知，以及任务总览的调度历史。不创建第三方账户，不以站点级凭证换取方便，不变更系统通知、安全或专注模式设置。

候选 `task-resource-notifications.mjs` 提供稳定事件 ID、两渠道独立持久 outbox 和 macOS `osascript display notification` 适配。文本作为参数传入，不拼接为 AppleScript 源码。每条事件保留任务、阶段、状态变化、原因与时间；后续协调器须补准确并行数量前后及看板任务稳定 ID，不只依赖可回收的三位任务号。

- 成功退出只能记录“系统已接受通知请求，显示未验证”，不能据此说用户已经看到。
- 发送前落盘 `sending`；发送后分别保存系统提交回执或看板追加回执。两渠道独立，通知失败不应阻塞安全调度。
- 重启发现 `sending` 转为发送结果不明，不自动重发弹窗。明确“未提交”的失败才有限退避，最多三次；结果不明保留待核实，不能无限制造重复通知。
- Mac 离线/休眠期间没有本机弹窗保证；事件先持久保存，恢复后区分尚未发送和发送结果不明，按原事件 ID 补处理。已确认提交过的通知不重弹；看板按幂等键补写。
- 通知泵单独运行，不与安全准入循环互相 await；持久outbox无法写入属于通知健康异常，仍须保留原调度状态中的事件，后续恢复导出。不得把局部通知故障扩展成释放锁或盲目重派。

### 看板接口核查与最小增量设计

看板现有 `task_history` 是CRUD快照历史；`update_task` 会更改业务更新时间/版本，没有独立幂等追加接口。不能把 `current_work` 或现有任务更新滥作高频日志。当前网站级 owner-private 服务 Bearer 不是事件专用窄权限，不分发给调度器。

建议由看板维护任务新增独立 `scheduler_events` 表与仅追加接口：`event_id` 唯一，绑定看板稳定任务ID、job/runID、时间、变化前后状态和并行数量、原因、是否测试。重复ID与同内容返回原回执，重复ID内容不同返回冲突。事件写入不改任务正文、状态或业务更新时间。界面在任务展开内容中展示近期调度历史。新凭证只能写事件，不能读站点/改任务，存放于受保护的Mac配置或Keychain，不入代码和日志。

该接口尚未实施/发放凭证，原生通知尚未真实发出。下一步由root协调一次清楚标为测试的本机通知及看板追加/去重验证；只有实测后才能称启用。模拟回执不作为真实送达证据。

### 方案 A 原生通知单次实测

已按用户选择及协调安排发送一次明确测试通知：“921 测试通知，不代表真实任务调整”。原生命令正常退出，回执为 `submitted`，横幅实际可见性仍为 `unverified`。未重复通知、未更改权限或设置、未调整真实任务。看板追加接口仍未建立，因此不称双渠道端到端完成。

现有 OAuth 路径无需新长期凭据，但需 agent 活跃处理或另获准的周期自动化，可能有额度消耗和同步延迟；不擅自建立定时任务。另发专用事件写入凭据须先明确范围、存储、撤销与替代方案并取得授权，当前没有生成任何凭据。本地 JSON/HTML 只算本地历史，不能冒充在线任务总览同步；浏览器读 localhost 还受跨源/私有网络权限及页面打开状态限制，尚未验证，不作为现成可靠替代。

### 本机可见性与持久事件联动

用户已明确确认第三次测试弹窗可见。此事实仅覆盖该次原生通知，不扩展为重启/后台长期运行或看板同步成功。另一次测试仅按用户再次明确请求发送，未修改设置。

新增 `task-resource-event-link.mjs` 从完整持久调度事件重建每次变化前后的并行组数，绑定稳定任务ID和显示编号，导出到双渠道outbox。准备准入、暂停请求、资源暂停、阻塞及阶段结束分别留痕；纯 `starting → running` 内部回执不再重复弹一次通知。缺少准确稳定任务映射时不猜测任务归属。事件导出/通知存储失败记录为独立健康异常，不阻断已经完成的安全准入判断；源事件保留供恢复后重新导出。重启重新导出保持相同事件ID，已提交通知不重复发送。看板接口尚未授权接入时保留未提交状态，不伪造落库回执。

# 动态资源调度（任务 921）

## 目标与边界

默认利用可用资源并行推进独立任务，出现资源压力时减少运行组，资源稳定恢复后自动重新推进因资源暂停的阶段。保留原测试、零跳过、失败诊断与证据要求，不通过弱化质量提速。保留 main、固定 5179、共享后端/数据库、用户 Chrome 和其他任务的运行身份。

现有 resource-lease 解决归属互斥，delivery queue 解决主线交付顺序，二者不是性能调度器。e2e-resources 仅提供可选 Linux /proc 观察。新机制不替代这些安全约束。

## 实现形态

项目 Node 脚本，不需安装第三方监控软件。后续常驻部署复用 macOS launchd。Skill 可说明任务登记入口，但不能替代实际采样、状态保存与进程控制。

当前候选已实现：纯调度决策状态机、独占生命周期锁和原子持久状态、Mac/Docker 只读采样、持久待送达事件模型、模拟测试。**尚未接入运行执行器、常驻服务和用户通知桥接，未接管任务，不能宣称自动暂停/恢复已启用。**

## 调度决策

- 同一仓库单调度器独占锁，工作组有不可复用的 job id、任务编号、阶段、工作目录、准确输入指纹、峰值资源预算、互斥资源、是否可安全中断。
- 初始上限 4 组，其中最多 2 个 Docker 重组；上限只是保险，不预留固定闲置。按真实预算、资源互斥和依赖计算能开几组，不把所有测试强制串行。
- 5 秒采样；Mac 与 Docker VM 的预算分别核对。保留 Mac 2 GiB、Docker VM 2 GiB、磁盘 10 GiB 的余量；Docker 配额不是 Mac 剩余内存。
- CPU 忙碌达 85%、内存压力、交换增长或 IO 拥塞时停止准入；压力持续 15 秒时请求减少一组。Docker 可用低于 1 GiB 时立即请求减少一组。
- CPU 降到 70% 以下且全部指标恢复连续 60 秒后逐次准入。未知、过期或失败读数不能视为资源充足。
- 计入已运行组的完整峰值预算，避免新启动尚未到峰值时过量准入；此做法偏保守，之后仅凭测量校准。

阈值为待真实运行验收的初始保守值，不是已证实最优参数。Mac memory_pressure 的 free percentage 只能作为可用内存估算，非空闲页精确字节。采样器保留原始含义，后续需连续样本计算 swap 增量并校准 IO/内存压力信号；不能拿单次快照直接宣布稳定。

## 暂停、恢复和证据

优先在阶段边界停止准入。需要主动减少占用时，只允许对调度器自行启动且身份核对正确、声明可安全重跑的阶段发送 SIGTERM；不使用 SIGSTOP，不全局结束 Chrome/java/Docker。实际子进程/容器控制适配必须核对 run token、PID 启动时间、专属进程组/容器标签，终止后验证已结束才进入“资源暂停”。无法证明归属、无法退出或共享服务异常，保留现场并阻塞，不擅自杀进程。

恢复不是从测试内部断点继续，而是仅重跑被中断的完整阶段。已完成的有效阶段证据保留，只有对应输入、依赖和环境指纹仍匹配才允许复用。普通测试失败、权限失败、证据缺失不得自动无限重试。最多 3 次资源中断后转诊断阻塞并通知。

重启恢复必须检查锁归属、记录进程是否真的结束及源码指纹；未证明时不重复启动。当前存储锁对异常退出 fail-closed，自动安全回收尚需运行身份适配验证。Mac 关机、休眠、离线时不能保证持续运行，唤醒/联网后恢复仍需验证。

## 主动通知

每次安排调整保存有序 outbox 事件：涉及任务、阶段、原/新状态、原因、时间。发送成功获得用户会话的真实 message id 后才标为已送达；本地日志不算送达。相邻内部 start/running 事件由桥接聚合为一次实际安排通知，不重复轰炸。发送失败保留待送达，有限退避重试；任务状态与通知送达状态分别展示。

必须接入可唤醒 root 或用户可达的受支持通知链路，并实测暂停、恢复和发送失败后的补发。不将本地脚本伪装成有聊天发信权限的服务。当前 outbox 模型已测试，真实送达未测试。

## 启用前剩余验收

1. 将现有验证器按可中断阶段登记；保留现有 lease/资源隔离和证据输入，不接管已运行中的组。
2. 完成执行器：源码校验、持久化启动意图、准确身份回执、容器/子进程归属和安全停止。
3. 实测双采样、健康/压力映射，确保共享 5179 和后端不受影响。
4. 在独立轻量假任务验证压力暂停、稳定恢复、失败不重试、旧 PID/变更源码阻断、崩溃窗口恢复。
5. 验证用户通知桥接送达，断开时保留事件且恢复后补发。
6. 与主协调者协商安装用户级常驻服务后，验证退出重启、睡眠唤醒和正常卸载。未部署前保持人工协调。

## 第二阶段候选：运行控制与门禁准入适配

新增 `task-resource-runner.mjs`，仅控制本次调度进程亲自创建的 detached 子进程组：先持久化启动意图，再启动，记录 PID/PGID/启动时间/run token；停止时逐项比对，只发送一次 SIGTERM。未知或已退出的 leader、重用 PID、外部容器、不可重跑阶段均拒绝。启动后存储失败保留控制器现场，不隐去可能存活的进程；日志写入失败不得报告成功。没有自动认领旧 PID 的入口，也没有自动清除旧证据锁。

新增 `task-resource-verification.mjs`，通过现有 `executeVerificationPlan` 的 `run` 注入点做阶段准入，不修改默认门禁。等待准入后再次校验输入指纹和命令/环境摘要，然后调用原 `runVerificationTask`，原任务参数、覆盖、报告校验、有效复用及首次失败历史保持不变。

两种暂停明确分开：

- **阶段边界暂停**：既有后端/浏览器门禁默认属于此类。已开始阶段正常结束，新的阶段暂不准入；资源稳定后恢复排队阶段。不承诺立即降低已运行阶段的占用。
- **受控中断重跑**：仅用于显式声明可重跑、没有外部容器生命周期、属于本调度器的独立进程组。需实测终止整个所属组，结束后才能重新排队。Docker/浏览器旧门禁不自动进入此类。

本轮运行控制与准入接口用模拟子进程、模拟准入服务独立验证；没有运行真实重测、真实发信、常驻安装或重启。当前尚缺实际队列 broker/常驻协调循环、旧门禁合作式中断和用户通知唤醒桥接，不把可测试接口称为已部署能力。

通知能力已核查：当前工具的 webhook 仅提供指定在线连接器事件，没有本地状态文件变更触发器。Node 脚本没有用户会话发信权限。可由 root 使用支持的持久自动化读取 outbox、发送后写入真实消息回执，但该链路尚未建立和实测；不能用日志、模拟 send 或定时器代替真实到达。是否能提供事件级及时通知仍有平台能力待确认。

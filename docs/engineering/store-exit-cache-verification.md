# 门店彻底删除后的浏览器缓存核验

本文记录用户确认的缓存清理实现边界，不替代 V1.3 门店删除规则，也不代表整个任务已正式交付。

## 目的与范围

销售订单和履约原型共用浏览器的 `zdm-order-prototype-v1:<tenant>:<store>:<identity>:<account>` 缓存。门店删除后，原门店身份可能已经失效，不能依赖原登录身份才能清理这些缓存。

仅在独立删除凭证证明门店已经彻底删除时清理对应范围。身份失效、401、403、断网、超时、空结果、记录冲突及服务异常均不能作为删除依据。真实后端的门店业务数据仍由既有删除流程处理。

## 只读校验接口

- `POST /api/open/store-cache-exits`，无需登录；POST 仅用于提交有限长度的查询条件，不改变业务数据。
- 请求只有 `fingerprints` 字段，为 1～100 个小写十六进制 SHA-256 指纹；请求体最多 8192 字节。
- 指纹为 ASCII 字符串 `zdm-store-cache-v1:<tenantId>:<storeId>` 的 SHA-256；它不是凭证或业务授权。
- 成功响应使用现有响应格式，`data` 仅包含本次提交范围中已证明删除的指纹，去重并排序。不返回门店、客户、订单、操作者或删除凭证明细。
- 独立记录必须可读、作用域正确且具有必要的持久化能力。只接受 `COMMITTED`；同一操作出现提交与回滚冲突时，不返回该门店。
- 每个服务实例在滚动一分钟内最多处理 60 次调用；超限返回 429。不保存访问者身份或 IP。当前限流不是多实例共享的全平台配额。
- 指纹可用于判断其对应范围是否已删除；不能承诺知道范围编号的人无法计算指纹。接口不授予任何业务数据访问权。

## 浏览器处理

1. 应用启动、恢复联网、回到前台以及可见页面每隔 60 秒核验已有缓存；同一页面并发请求合并，每批最多 100 个范围。
2. 请求不携带登录凭证，五秒超时。仅接受响应成功、格式正确且属于本次请求的匹配结果；失败保留缓存，后续触发时重试。
3. 确认删除后先使当前门店访问状态失效，再清空对应内存状态、删除匹配的缓存。不清理其他门店、其他用途的浏览器数据。
4. 保存最小的指纹删除标识，避免旧身份响应或刷新页面重新启用已删除范围。其他标签页收到该标识时立即停止使用对应内存状态；缓存移除仍依赖已核实的删除结果。
5. 本地存储操作失败时记录为待处理，保留未成功删除的缓存并重试，不报告全部清理成功。
6. 浏览器关闭或离线时无法远程清除其磁盘内容；重新打开并联网后再核验。以上机制不是远程擦除设备的能力。

## 必要历史姓名

只有实际保留的历史记录需要引用已删除账号时，才保存必要姓名。独立成功凭证包含这些姓名快照，恢复旧数据库时以该凭证恢复，不使用旧备份中的过时姓名替换。

凭证缺少必要姓名、内容损坏或范围不一致时阻断恢复，不猜测补齐。门店专属账号按 V1.3 处理；租户专属账号沿用原有账号生命周期规则。

## 验证与发布边界

单元测试覆盖匹配范围、失败保留、请求限制、并发及跨标签页失效；页面自动化覆盖失效登录清理、旧响应保护和原有订单、履约、款项配置行为。后端测试使用隔离数据；真实预览仅做只读接口、健康与数据保留核验，不删除真实门店来验收。

业务专项通过与整个旧任务正式交付分别记录。旧分支与新主线的回归登记差异不能通过覆盖其他任务测试或放宽校验来消除；交付时仍需完成适用的主线组合与完整门禁。

## 本轮接入补齐

- 门店删除结果同时读取本次媒体候选对应的未解决回收任务。入队成功只表示移交成功；等待执行仍显示待处理，实际回收失败显示需核验。正常保留期、人工保留和共享引用继续使用原有媒体生命周期，未更改回收期限。即使原移交阶段已完成，后续到期回收出现故障也会在结果中反映。
- V172为安全审计追加最小身份、组织快照字段，不增加业务正文，也不建立指向活组织的外键。新请求在业务执行前捕获快照，结果状态仍在执行后记录。旧记录仅在门店退出前按可核实身份关系补存组织信息，来源标记为`store-exit`，不冒充事件发生时的名称。恢复时使用独立删除凭证的门店、租户名称及时间，来源标记为`exit-recovery`。无法关联的旧记录不猜测归属，目标范围存在冲突时阻断删除。
- 已确认删除的当前门店会话同步清除失效令牌、身份资料及旧权限；没有订单缓存时也核验当前门店范围。其他门店的当前会话、账号及缓存保持不变。收到迟到结果时重新核对当前身份，避免清除刚切换的新会话。

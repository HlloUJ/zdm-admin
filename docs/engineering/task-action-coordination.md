# 按动作调度与接续

装点猫管理后台的任务继续使用现有受理回执、真实执行者、执行顺序账本和最终 main 队列。独立开发、准备、PR 与初始 CI 可以并行。最终组合、合并、main CI 与共享运行交接仍在原最终队列串行。真实用户暂停、来源保护、原冻结和完整门禁继续生效。

## 动作与依赖

- 动作包括 `development`、`preparation`、`combination`、`runtime` 和 `final`。旧 `dependsOn` 保留原正式交付依赖语义，不能通过新字段取消。
- 已获授权的任务执行者可在冻结前通过 `task:entry -- --worktree <准确目录> registry action-dependencies --task <ID> --expected-revision <登记版本> --requirements <JSON数组>` 登记动作依赖。每条记录声明 `task`、`actions` 和 `evidence`。源码与运行证据另需固定 `head`。正式交付依赖核对关闭、完整回执与主线祖先。源码依赖核对已登记的干净自有 checkpoint。运行依赖复用独立预览租约、API 健康与独立数据来源校验。
- 单独准备无关的开发与 PR 时，联合源码与运行依赖不阻断准备。涉及依赖的实际动作重新核验对应证据。动作与职责变化由真实授权覆盖；登记动作依赖不会扩大执行或交付授权。

## 只读接续

从已发布 main 运行 `npm run task:entry -- continuation <准确任务ID>`。它读取登记、候选与索引身份、原冻结、票据、完成记录、镜像锁、仓库已知的端口和最终共享资源。报告区分普通源码重叠和可由现有 Git 对象证明的受保护删除／修改冲突。报告标明来源或资源证据缺失、具体受影响动作以及当前可继续项。报告不创建票据、准备数据、启动服务或运行测试，也不证明未来的源、环境或资源状态。运行证据的现状检查仅在被声明的动作需要时执行。

当前总协调可从原私有宿主桥使用 `continuation-plan` 或 `coordination-plan`。后者凭既有 `authorityId`、真实当前协调者、登记任务、当前板卡、原执行者与新鲜容量，给出具体等待项与下一入口所需的身份和版本。每次进入原派发入口时单独生成新的决定 ID，执行后的账本变化需重新读回。它先考虑能解开共同依赖的可执行动作，条件相近按原真实收件顺序。旧模式仍能读取原账本，动态决定通过已有持续授权和准确派发入口进行。准备不占最终 main 范围；用户暂停或容量不明时不给出可发出的动作。

## 空闲容量与下一动作

`capacity-release` 仅处理原有 `blocked` 票据，校验准确 admission、看板 revision、任务与执行者、当前受信委托、原候选和新鲜本机空闲证明。指定 `nextAction`，并以 `recovery` 记录具体恢复条件。依赖等待使用 `{kind:"dependency",task,reason}`，本机资源等待使用 `{kind:"resource",reason}`。有活进程、容器、锁、正式交付会话或未知 CI 时继续保留现场。动作只释放执行容量，原票据、失败、接续点、冻结和资产继续保留。

活动协调回合用 `coordination-observe` 持久记录真实依赖或资源读回变化，用 `coordination-plan` 读取待处理事件。已发出准确的持久派发预约后，用 `coordination-record` 关联来源事件与预约编号。暂时不可继续时记录准确等待原因。正式关闭事件可以按原 main 和关闭回执记为已处理。相同事件读回使用原结果，不能再次发送或启动。实际消费依旧需要重新证明权限、源码、依赖、执行者与容量。没有协调者处置时，事件保留在账本。现有监测继续负责状态观察，项目未增加常驻调度服务。

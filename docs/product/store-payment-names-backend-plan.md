- src/pages/order/prototype/resources.ts：款项配置权限资源。

## 2. 数据模型

建议新表 store_payment_names。采用门店组织私有数据，不能按创建账号分库或按账号分配不同配置副本。

| 字段                              | 用途                                                                                     |
| --------------------------------- | ---------------------------------------------------------------------------------------- |
| id                                | 服务端生成且稳定不变的配置ID；API序列化遵守现有长整型约定，避免JS精度丢失。              |
| tenant_id、store_id               | 服务端从合法当前身份取得，按现有组织归属关系约束。                                       |
| name                              | 展示名称，最多10个字符；前端输入限制、服务端新增及编辑校验同步执行，唯一性规则见PRD D2。 |
| enabled                           | 启用或停用，新建默认启用。                                                               |
| created_by_account_id、created_at | 统一账号ID及服务端创建时间；不可由编辑接口覆盖。                                         |
| updated_by_account_id、updated_at | 最后变更的账号及时间。                                                                   |
| version                           | 内部乐观锁版本，每次成功变更递增；不作为用户管理的历史版本。                             |
| deleted_at、deleted_by_account_id | 记录逻辑删除；所有正常查询显式排除。                                                     |

索引：组织范围加创建时间及ID，支持稳定倒序列表；组织范围加启用状态，支持选项读取。

按已确认的D2、D3规则：增加仅对未删除记录生效的名称唯一约束。例如生成列 live_name = CASE WHEN deleted_at IS NULL THEN name ELSE NULL END，按tenant_id、store_id、live_name建唯一索引。显式使用符合大小写比较规则的排序规则，避免MySQL默认不区分大小写而与前端行为冲突。不能仅做SELECT查重后直接INSERT。

不预置款项数据。迁移编号按实施时最大有效版本顺延，不提前指定固定Flyway版本。

## 3. 后端分层

建议以StorePaymentName为业务对象，形成Controller、Service、Mapper、Entity、CreateRequest、UpdateRequest、StatusRequest及Response。

- Controller：参数校验、统一权限守卫和ApiResponse封装。
- Service：当前门店范围、名称规则、事务、查重、版本冲突、软删除和审计。
- Mapper：所有读写带合法组织范围；不能只按ID更新或删除。
- 写操作事务内重新校验归属和状态，更新条件同时包含组织、ID、未删除条件及版本。
- 创建人列表展示复用统一账号名称解析；操作日志采用发生时的操作者和名称快照。

本次使用独立配置操作事件表持久化，记录新增、改名、启停和删除的前后值及操作者。只记录已提交成功的变更；不为此新增日志菜单或更改全系统日志能力。组织归属由服务端强制校验并持久化；本次不新增组织级联删除外键或门店生命周期处理，不修改既有门店删除流程，也不自动清理配置与审计历史。

## 4. API草案

拟定基础路径：/api/store/payment-names。最终遵循现有门店控制器的路径及响应约定，不擅自创建第二套鉴权或错误协议。

| 方法及路径                               | 请求要点                  | 响应及强制点                                                                      |
| ---------------------------------------- | ------------------------- | --------------------------------------------------------------------------------- |
| GET /api/store/payment-names             | page、pageSize            | 当前门店分页列表及total；创建时间、ID均倒序；要求配置查看权限。                   |
| GET /api/store/payment-names/options     | 无门店参数                | 仅返回启用未删除项的id、name、version；仅供具有配置查看或有效收款登记能力的身份。 |
| POST /api/store/payment-names            | name                      | 新增配置；要求create；后端生成归属、创建信息和启用状态。                          |
| PUT /api/store/payment-names/{id}        | name、version             | 仅修改名称；要求edit；拒绝以此接口顺带改状态、门店或创建人。                      |
| PUT /api/store/payment-names/{id}/status | enabled、version          | 提交目标状态，不提交“取反”动作；要求toggle-status，防止重试反复切换。             |
| DELETE /api/store/payment-names/{id}     | version（按现有传参惯例） | 要求delete；按D3处理，事务保留审计信息。                                          |

管理列表不返回其他门店记录。选项接口不返回创建人、完整审计等管理字段。

没有现存“详情”入口，不为凑CRUD新增详情页面；确有编辑数据刷新需要时再在同一权限内设计读取，不扩大页面范围。

返回字段建议为id、name、enabled、createdByAccountId、createdByName、createdAt、updatedAt、version。错误使用项目既有响应结构与HTTP映射；需要区分名称重复、版本冲突、记录不可访问、无权限和参数错误，但不另编造一套未经验证的错误码规范。

## 5. 身份、权限与并发

1. 复用现有当前身份提供者，确认当前有效身份属于合法门店；读取tenantId和storeId，不接受前端覆盖。
2. 显式消费既有nature.view/create/edit/toggle-status/delete权限。终端允许范围、角色和适用数据权限继续走统一体系，不使用原型预览放行函数作服务端鉴权。
3. 同门店配置共享不等于全部人员可写；创建人不是私有数据过滤条件。
4. 跨店ID与不存在ID按同一不可访问语义处理，避免泄露对象存在性。
5. 唯一约束处理并发重名；通过事务内当前读加行锁及版本比较判断冲突，不最后写入者静默覆盖。
6. 状态API使用目标值；重复请求同一状态不得反转。重复删除的处理遵循统一接口约定，不能误删后续同名新记录。

## 6. 前端接入

- 新增src/services/storePaymentNames.ts，复用项目request、认证和错误处理入口。
- 配置列表、total及分页改从接口取得；前端不再对单页数据冒充全量分页，也不再自行用客户端时间生成创建信息。
- 保留现有列表、表单、确认弹框、启停、删除入口和成功Toast；不改样式、菜单层级或字段名称。
- 新增、编辑、启停、删除成功后刷新合法当前页；删除末项时校正页码。
- 弹窗提交锁定期间防止重复点击；失败保留输入，成功后才关闭。
- 原型中配置相关函数拆出API消费，不整页重写销售订单、履约或价格逻辑。
- 订单原型的localStorage状态仍保留其订单等模拟数据，但paymentNames不得继续作为真实配置的数据源或被watch回写恢复；清理仅限当前作用域的旧配置字段，不能删除整份原型状态。
- 不把各浏览器的旧配置自动上传或导入数据库。首次上线真实配置为空是“未迁移”，不能对用户谎称旧数据已同步。需要导入时另行确认来源和冲突策略。
- 切换身份或门店时清空列表和选项缓存；使用请求取消或作用域版本令牌阻止旧请求覆盖新门店结果。退出登录释放该会话缓存。
- 接口失败明确报错，不回退localStorage，也不重新灌入默认首付款、定金等数据。

## 7. 对订单与收退款的最小适配

真实款项配置上线后，收款选择器调用受权限保护的选项接口。原型本地登记继续写nature名称快照，不因配置刷新而反向更新旧Payment。

如果需要保留新选择的配置身份，可为原型Payment新增可选paymentNameId及版本元数据；旧记录允许为空，不猜测补齐。此适配不得改变订单金额、状态或已有收退款校验。

未来收退款后端接入时，真实提交须使用配置ID，由服务端在同一事务内校验当前门店、未删除且启用，按提交版本确认名称，写入payment_name_id及payment_name_snapshot。不能信任客户端自由提交的名称快照。

本次没有真实收退款接口，因此不能把“配置刚停用后拦截真实收款”列为已经可实现的服务端保证；本次只完成配置后端和原型消费，后续另验真实收款提交闭环。

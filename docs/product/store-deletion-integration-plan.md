# 门店退出统一接入机制（已确认方案）

日期：2026-11-06

状态：用户已确认范围已实施，完整本地门禁及5175受保护升级、只读联调通过。实施证据与其他环境部署边界见[运行说明](store-deletion-implementation.md)；未执行真实门店删除、推送或合并。

## 1. 权威与本次边界

门店彻底删除的统一业务规范为Notion有效的[门店彻底删除数据处理规则V1.3](https://app.notion.com/p/410572fed03281868f44d43c94b8a448)。账号、媒体及真实交易等专项规则按V1.3引用和适用，不因本方案被排除；规则冲突先统一，不由实现自行选取。本文件规定已确认的接入与验证边界，不复制规范、不新增保留例外或期限。

本次已获授权实施以下接口、操作记录、独立恢复保护、存量接入及门禁。真实门店数据删除、推送与合并不在本次授权内。存量范围见[模块调整清单](store-deletion-module-audit.md)。

## 2. 一次登记，两个入口共用

建议设置门店退出协调入口，门店单删及租户联删门店都调用它；租户自己的非门店数据仍归租户退出流程，不扩大本次规范到其他主体。

租户联删时，门店参与模块加入租户入口现有的同一主库事务，不按门店单独提交；任一参与模块失败回滚该次主库清理。共享账号在本次目标关系全部解除后统一判断；租户、门店与共享依赖按固定顺序加锁，避免两个入口并发重复处理或死锁。

各模块通过固定内部参与接口接入，协调入口自动收集；同一数据范围只能有一个明确的执行归口，重复声明、依赖缺失或依赖循环须在执行前阻断，不允许通过忽略参与方继续。不在两个删除函数里分别追加SQL名单。登记负责把已确认规则映射到实际数据，不是第二份业务政策。

每个参与模块登记：模块ID、实际主/子表、组织范围推导、各状态记录、间接关系及业务域引用、处理动作与规则依据、依赖、收尾类型、独立校验及测试证据。保留项同时记录有效依据、到期条件及起算事件；没有已确认期限时不编造天数，也不把重试、任务重建和恢复当作新的起算事件。不只登记store_id列；公共/租户级/系统数据也须明确不随门店处理的理由。

表、数据集和业务域按实际归属拆分；同一模块或同一表可以有不同处理类型。纯历史标识与需要保留活主体的业务引用分开登记，不能把所有_account_id列视为同一种引用。

建议内部接入能力如下，不新增面向客户端的任意组织清理接口：

| 能力       | 职责                                 | 限制                                                   |
| ---------- | ------------------------------------ | ------------------------------------------------------ |
| 覆盖声明   | 声明真实数据路径、依据、依赖和测试   | 不能靠空声明、保留全部或不适用逃避覆盖                 |
| 预检       | 返回清理数量、保留理由、责任和阻断项 | 只读，只返回有权查看的摘要                             |
| 事务内执行 | 使用受限目标上下文处理本模块数据     | 加入协调入口的同一主库事务，不独立提交、不删物理文件   |
| 独立校验   | 读取实际结果，检查残留及保护对象     | 不只相信删除函数的返回值和自报数量                     |
| 提交后收尾 | 处理媒体、受控副本及必要后续工作     | 使用持久化任务，作用范围绑定原操作，不依赖已删门店登录 |

目标上下文由协调入口根据当前合法操作、数据库门店与租户关系、规则版本生成；不接受模块从客户端取tenantId/storeId覆盖范围，也不通过临时切换门店身份调用要求门店运营中的公共删除接口。

## 3. 执行与状态边界

建议使用内部删除操作记录、收尾任务和退出事件，分别承载目标/版本/计划指纹/操作者快照、阶段结果、幂等键和重试所需的最小资源标识。凭证内容完整对应V1.3第五章的最小必要字段，不能省去各模块数量、保留依据或校验结果；记录访问和收尾执行继续受权限与目标范围限制。它们是技术过程记录，不新增门店经营状态、恢复入口、固定审批或完整业务备份。具体表和字段在实施前按最小需要设计。

1. 确认目标门店已归档，操作者具有相应删除权限和数据范围；归档本身不触发清理。预检聚合实际模块结果；引用未处理、未完成责任无接续、覆盖不全等直接阻断。进入会造成不可控残留的主数据删除前，必须已具备并核实在线副本的可靠隔离、经营写入约束及持久化收尾能力；不能先删主库，再等待这些能力补齐。
2. 运营确认准确目标及摘要。保留现有权限编码、菜单和样式；必要的预检/结果展示复用官方组件。V1.3没有单独批准“输入完整名称”交互，本方案不将其冒充现行必填要求。
3. 主库事务内锁定目标及必要依赖，协调门店单删/租户联删，复核权限、归属、规则/结构兼容性和预检条件。按依赖排序执行所有参与模块，最后处理门店主档。
4. 删除执行后、事务提交前，独立校验主库应删残留及共享对象保护结果；不符合计划即回滚。成功凭证、必要收尾任务及提交事件与主数据同事务保存，且不被门店/租户的级联删除带走；事务内任一步失败回滚。失败/拒绝审计独立保存，不能误记成功。
5. 提交后执行持久化收尾，识别已完成、待执行、失败和结果不确定部分；不以无限重试冒充完成。
6. 分别核实数据库、在线副本、媒体生命周期及保留项，按V1.3第十章报告数据库阶段、必要收尾与全部完成的准确结果；正常生命周期保留不误报故障。不能只因主档不存在就认定全部删除完成，也不能承诺擦除人员自行下载或未联网终端的全部副本；这些边界须在执行前告知。

并发写入入口也须遵守同一组织退出约束：只锁门店删除端不足以阻止无外键数据在旧请求中晚到写入。实施时审查普通写入、系统任务和消息回调的共同约束，不把组织退出顺手扩展为其他业务状态调整。

实际规则或结构变更影响未完成计划时，暂停相关剩余动作并复核；不假回滚、不重复交易动作、不扩大历史清理范围。仅在变化影响原确认含义时重新告知运营，普通技术恢复不增加业务审批。

## 4. 恢复保护必须独立设计

主库内一张删除记录表会跟随旧备份回退，不能单独满足V1.3。建议采用主库事务记录与独立恢复保护存储配合：

- 不可逆清理开始前，在独立存储可靠登记目标和操作的受理/意图，不能标为成功。
- 主库事务提交成功后，通过可靠退出事件同步最终结果；主库与外部存储不能被宣称为单一原子事务。
- 存在未决意图但无法证明最终提交结果时，恢复流程先保持目标范围不可用，再根据可信记录核实，不把意图直接当成功，也不自动恢复经营。
- 恢复旧备份后，按最新有效结果重新落实清理，校验完成后再开放相关读取、导出、同步和经营；不重做退款、发货或扣库存。
- 独立存储的权限、持久性和恢复证明须单独验证。未实际配置前不宣称已经实现独立防绕过或灾备保证。

机制设计不预定外部供应商。确认后的本地独立存储部署及维护边界见[运行说明](store-deletion-implementation.md)，不清理任何备份；其他环境需分别配置和核验。

## 5. 计划中的强制验证

| 层次       | 检查内容                                                                 | 失败处理                                            |
| ---------- | ------------------------------------------------------------------------ | --------------------------------------------------- |
| 结构覆盖   | 在隔离数据库应用迁移，核对真实表、关联和模块声明；非门店/系统表明确列示  | 未覆盖或归属不明不得静默通过；不根据列名生成删除SQL |
| 接入一致性 | 实际参与模块与声明一致，处理器和校验能力存在，两个入口共用               | 缺处理器、空实现或遗漏参与方失败                    |
| 删除契约   | 多租户、多门店、各状态、混合关系、共享保护、账号历史、媒体域、回滚与并发 | 原始数据及保护对象独立核验，不只看接口200           |
| 重试与恢复 | 重复请求、主档已无但有残留、规则变更、提交后中断、未决意图及旧备份恢复   | 不确定结果先核实，不改历史基准来通过                |
| 运行时预检 | 实际版本/结构/参与能力与当前计划匹配                                     | 阻止受影响的彻底删除；不扩大为停止无关正常业务      |
| 本地与CI   | 接入现有验证和适用必需汇总检查，保留完整报告与首失败                     | 无证据不标完整，不靠跳过或削弱断言通过              |

自动发现结构不能替代业务归属判断。候选不能仅修改自己的声明和测试来证明“没有遗漏”；需独立结构清点、真实结果测试和受保护的规则/基准变更审查。远程必需检查和独立保护未配置前，准确报告保护等级。

## 6. 建议实施顺序与本次确认范围

1. 建立受限协调入口、模块登记、只读预检及操作/任务模型。
2. 按清单补齐现有模块，打通两个入口，保持范围外业务行为和UI不变。
3. 补上事务、并发、失败留痕、媒体/副本收尾和恢复保护。
4. 接入结构/模块覆盖与契约测试，再配置和验证CI、运行时阻断。以上阶段均先在隔离环境完成；全部必要保护及符合性验证通过前，不开放或切换真实门店的删除执行入口，不能把分阶段开发当作分阶段解除保护。
5. 按V1.3逐条复查，提供真实结果、剩余阻点及回滚/数据保全边界。

用户已确认这套机制及存量调整范围，不逐表重定已明确的删留政策。该确认不授权立即清理现有持久数据；真实删除试验优先使用隔离测试库，长期预览迁移或实际数据清理继续遵守准确目标、备份和授权边界。

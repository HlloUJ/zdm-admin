## 1. 目标与范围

将原有门店管理模块中的商品选择弹窗，调整为新标签页中的独立“选品中心”。门店先挑选商品加入选品清单，再统一确认加入本门店对应仓库。

本期不包含采购、支付、推荐、自动上架、实物库存划拨及新的供应链采购流程。商品加入门店仅建立门店商品记录，不代表门店取得实物库存。

供应链继续维护来源商品，运营端继续维护平台上架范围；选品中心消费既有商品、分类、媒体、价格及库存能力，不替代上游维护模块。

## 2. 确认边界与待确认项

### 2.1 已确认规则

- 以第24版为页面视觉基准，不重新设计整页。
- 原成品现货管理、配件管理的“商品中心”按钮作为入口，新标签页打开，页面名称为“选品中心”。
- 默认展示成品现货和配件，可通过两种类型筛选查看一种或同时查看两种。
- 默认仅查看未加入门店商品；支持查看已加入门店商品。
- 无对应类型维护权限时仍可浏览，禁止加入，并展示具体无权限标签。此规则替代早期“隐藏无权限类型”的讨论。
- 已售完商品仍展示，不能加入清单或门店。
- 门店回收站记录仍算已加入；不同门店分别判断。
- 商品浏览按供应链创建时间倒序；清单按加入清单时间倒序。
- 平台分类支持1至4级，任意一级可单选查询该分类及全部后代商品。
- 批量加入允许部分成功；统计总数、成功数、失败数，仅列失败明细。
- 同一门店多个员工并发加入同一商品，只允许一次成功，后续项失败并说明原因。
- 正式实现清除效果展示数据、演示入口和模拟业务逻辑。

### 2.2 待确认的产品决策

**D-01：清单归属。**建议按“当前账号＋当前门店”持久保存。这样不同员工可以各自选品，同一账号在不同门店也互不干扰。用户已明确多个员工可能分别把同一商品加入清单，但尚未单独确认清单归属及持久保存方式。本文后续清单设计以此建议为前提；正式实施该持久化范围前需确认本条。

接口名称、内部类名、表名为实施建议，不属于界面正式文案。实施时可以按项目现有命名调整，但不得改变本文产品行为。

## 3. 使用路径

1. 员工从原管理模块点击“商品中心”，新标签页打开选品中心。
2. 浏览、搜索或选择平台分类，查看商品详情。
3. 对可选商品点击“加入清单”，更新清单数字小标。
4. 打开选品清单，按成品现货、配件切换检查、移除商品。
5. 点击“加入门店”，提交本次整份清单中的商品，不仅是当前Tab或当前页。
6. 展示批量处理结果；成功商品进入对应仓库并移出清单，失败商品保留。
7. 返回原管理页面时刷新数据，能看到新加入仓库的商品。

登录过期后按现有认证流程处理；新标签页必须重新验证当前登录身份和门店，不信任链接中携带的组织参数。

## 4. 商品浏览页面

### 4.1 页面结构

- 保留装点猫图标及“选品中心”名称、当前门店、商品浏览和选品清单入口。
- 不出现设计评审工具栏、方案切换、权限模拟开关、演示说明或页脚。
- 搜索框包含商品分类入口、商品名称输入和搜索按钮；只按商品名称搜索，不把ID、规格或价格偷偷纳入匹配。
- 普通状态下四个轻量文字筛选为“成品现货、配件、未加入门店、已加入门店”。
- 商品类型、加入状态各自为可多选组；组内选项取并集，两组与名称、分类条件取交集。两项都选中表示该组不限制，均取消也表示该组不限制，避免意外得到无意义空条件。
- 默认类型两项均选中，状态仅“未加入门店”选中。
- 列表采用五列商品卡片；卡片展示主图、名称、门店适用价格、状态标签和加入清单操作。
- 点击卡片打开详情，不设置独立“详情”按钮；点击加入按钮仅执行加入，不冒泡打开详情。
- 悬停采用已确认的轻微浮起和图片缩放效果，不重新增加重阴影或长动效。

### 4.2 查询与分页

- 服务端合并两类商品的合法查询结果，统一排序后分页；不能各取一页再在前端拼接。
- 主排序字段为供应链商品创建时间，倒序；相同时间按稳定的商品类型与ID次序打破并列。
- 供应链创建时间不可用时不得用运营上架或门店加入时间冒充，需核对既有数据并报告异常。
- 商品名称输入后按搜索按钮或回车查询；分类选中、类型或状态变化立即查询并回到第1页。
- 名称支持去除首尾空白后的包含匹配；SQL参数化处理，输入中的通配符按文字处理。
- 商品浏览默认20条/页，保留第24版选项10、20、40；修改页大小回第1页。
- 总数按全部有效查询条件计算，不只计算当前返回页。
- 分页复用系统公共组件与现有规范：16px内边距、不叠加额外外边距、窄容器按公共规则重排。
- 空结果使用真实空状态；请求失败展示错误并允许重试，不用静态商品填充。

### 4.3 吸顶与分类弹层

- 滚动超过已确认顶部区域后，切换为紧凑吸顶栏；保留图标和“选品中心”。
- 搜索框与四个筛选作为整体居中；紧凑状态四项改为统一尺寸图标，悬停显示轻量中文提示，默认不常驻说明。
- 分类弹层鼠标移入打开，移出关闭；向上/向下箭头准确反映开合状态。
- 弹层左侧始终与整个搜索框左边缘对齐，空间不足时收窄并换行，不向左挪动避让。
- 延续第24版尺寸规则：最大宽1200px、最大高560px；视口右侧及底部至少16px，内容超高时内部滚动。
- 成品现货、配件并排，悬停切换对应的平台分类树；两棵树独立维护，不能混用ID或名称映射。
- 不显示“一级、二级”等级别文字。所有层级均可点击，单选后关闭弹层、立即查询。
- 选中父分类包含其所有后代，选中末级仅查询该末级。后端计算后代，不依赖前端提交叶子ID集合。
- 通过搜索框内清除按钮取消分类，仅清除分类条件，保留名称、类型及状态筛选。
- 分类名称字号跨浅层与深层结构一致。
- 分类字体（2026-11-13验收确认）：一级保留原加粗样式；二、三级仅在有下级时使用次级灰色，无下级的末级类目使用正文深色；四级保留正文深色。选中项保留品牌色，不由默认文字色覆盖。
- 分类连接箭头：二级有下级显示、无下级不显示；三级全部不显示。仅有两层的浅层根节点保留现有到子项的连接箭头；箭头与文字垂直居中。

## 5. 商品范围、状态和价格

### 5.1 可浏览条件

商品必须运营端正常上架、未删除且未失效，供应链状态为已上架或已售完。供应链下架、运营端下架、删除或失效后不再进入浏览结果。

浏览条件不再以“库存必须大于0”过滤，因此已售完商品仍可见。是否已加入门店不决定平台可浏览资格，只决定加入状态和筛选结果。

### 5.2 状态与操作

| 条件                               | 标签/提示                           | 加入清单   | 加入门店                               |
| ---------------------------------- | ----------------------------------- | ---------- | -------------------------------------- |
| 可浏览、未加入、未售完、有对应权限 | 无异常标签                          | 允许       | 提交时再校验                           |
| 在当前账号当前门店清单中           | 已加入选品清单                      | 禁用       | 由清单统一提交                         |
| 当前门店已有记录，含回收站         | 已加入门店                          | 禁用       | 失败：该商品已加入门店，请勿重复添加。 |
| 已售完                             | 已售完                              | 禁用       | 失败：该商品已售完，无法加入门店。     |
| 无对应维护权限                     | 无成品现货维护权限 / 无配件维护权限 | 禁用       | 失败并说明对应权限不足                 |
| 来源下架或失效                     | 浏览不展示；清单保留异常项          | 不允许新增 | 失败并说明实际状态                     |

状态分别由服务端返回，不能用一个含义模糊的布尔值覆盖。清单、售完、已加入和权限不足可能同时出现，不能隐藏有效原因。沿用已确认的不同标签风格；加入按钮保持同一种操作文案并使用原生禁用态，不用按钮文案替代状态标签。

### 5.3 价格

- 列表区间及详情SKU价格均复用当前门店级别的有效价格规则，由服务端计算。
- 列表区间由有效SKU价格得出，详情展示每个SKU的实际价格；不将区间复制到每个规格。
- 不向无权调用方暴露其他门店级别价格、成本或加价内部配置。
- 缺少必要价格配置时按既有价格完整性规则返回明确状态，不伪造0元、不套默认门店级别。
- 清单不保存一份永久不变的演示价格；读取和提交时核对当前有效数据。

## 6. 商品详情

### 6.1 媒体和滚动

- 使用真实主图、图集与视频。存在视频时优先展示视频，默认静音自动播放并保留播放控制；浏览器阻止自动播放时可以手动播放。
- 只有图集或只有视频时不显示媒体类型切换；两者同时存在才显示切换。
- 缩略图不增加文字说明；按比例居中展示。超过可见缩略图数量时可内部滚动，隐藏缩略区滚动条。
- 左侧缩略区与右侧主媒体区等高，沿用已确认的适配与图片比例规则。
- 打开详情锁定背景商品页滚动；详情正文仍可滚动，滚到边界后不带动背景。关闭和卸载后恢复原滚动样式及位置。
- 名称与价格字体同列表一致，价格放名称下方；分区标题使用“基础信息”“销售信息”。

### 6.2 基础信息动态渲染

- 固定业务字段仅展示接口实际提供的商品类型、分类等合法信息。
- 类目配置的商品属性按商品实际保存的字段、名称、值及展示顺序生成，不写死材质、颜色等演示字段。
- 沿用每行4个字段的确认布局；字段数量变化自然换行，不补空白占位字段，窄屏不溢出。
- 使用统一空值展示规则；未配置字段不生成，已配置但未填写与数字0、布尔false必须正确区分。
- 历史商品保留其已保存的属性/规格语义，不直接套用类目最新模板而丢失、错配或重命名已有数据。

### 6.3 销售信息动态渲染

- 使用真实规格维度、维度顺序、SKU、销售属性、单层/分层模式及展示顺序。
- 单层规格按单层展示；分层规格按商品保存的层级关系展示，并使用既有分组/合并能力。
- 不按展示名称猜测层级，不把树状配置强制压成固定两行，不生成“标准款、加宽款”。
- 销售属性列由该商品实际配置决定；展示名称与存储键明确对应，字段多时使用分区内横向滚动，不撑破抽屉。
- 每个SKU价格、库存及属性必须与其SKU标识对应；层级合并后不能漏行、串价或重复累加库存。
- 已售完商品仍可查看合法详情，库存0按0展示。
- 列表、清单和详情共用状态判定及价格来源，避免同一商品显示互相矛盾。

## 7. 选品清单

以下持久化范围以D-01确认采用为前提。

- 以账号＋门店持久保存；刷新、关闭页面后保留，不同账号、不同门店互不干扰。
- 同一清单内“商品类型＋来源商品ID”唯一；不同员工可以各自加入同一商品。
- 重复加入当前清单不新增记录、不改变原加入时间。移除后重新加入使用新加入时间。
- 清单按加入时间倒序，相同时间按清单记录ID倒序稳定排序。
- 清单在成品现货、配件之间分Tab展示，分别分页，默认5条/页、选项5/10/20；切换Tab回第1页。
- 清单数字小标和右侧汇总统计全部清单，不受当前Tab、页码影响；“加入门店”处理全部清单。
- 不展示“查看详情”链接，点击商品行/卡片打开详情；红色“移除”不冒泡打开详情。
- 商品行用浅色虚线分隔，无悬停背景；操作标题和移除按钮左对齐。
- 当前类型为空时不展示商品信息、价格、操作表头及分页，空状态在可用区域居中；整个清单为空时展示已确认的完整空状态。
- 空清单说明：去发现适合门店的商品，加入选品清单后，在这里统一确认，并添加到仓库中。
- 右侧说明使用次级字体：加入门店后，商品将分别进入成品现货管理、配件管理的仓库。
- 已在清单中的商品若售完、下架、权限变化或被其他员工加入门店，保留记录并返回具体不可加入原因，允许移除。
- 提交成功项移除；失败项保留。删除末页最后一项时回到仍存在的合法页码。

## 8. 权限和组织隔离

- 复用现有入口权限；不新增顶级菜单或自动授予既有角色新权限。
- 从任一已授权商品中心入口进入后，可浏览两类合法平台商品及其门店适用详情，但对应类型的加入操作必须具备该类型选品/维护有效权限。
- 实施时核对当前功能资源编码；现有选品动作分别为`store.finished-stock-management.select`、`store.accessory-management.select`。不能仅根据“维护”中文名称推断需要另授编辑或删除权限。
- 不能因支持跨类型浏览而开放其他模块的编辑、上架、删除或成本数据接口。专用浏览接口必须限制返回字段。
- 所有接口均验证登录身份、合法门店、数据权限与相关功能条件；门店归属由服务端写入，忽略或拒绝客户端伪造的作用域。
- “已加入门店”查询必须包含当前store_id；不能使用全平台是否有人选中过来判断。
- 清单查询、数量、详情、移除、批量提交及结果查询使用一致归属；其他账号的清单和批次不可通过猜测ID访问。
- 身份或门店变化时清除旧页面数据与缓存，重新验证；旧标签页不得静默把旧清单提交到新门店。

## 9. 批量加入门店与并发

### 9.1 提交范围和处理

- 提交时固定当前清单记录集合，作为本批次快照；之后新加到清单的商品不混入本批次。
- 服务端逐项核对权限、组织、来源状态、售完/可供条件、当前门店已有记录、价格完整性及现有加入流程的关联条件。
- 每项独立事务，一项失败不回滚其他成功项；单项内仓库记录、必要快照、价格初始化、入库来源及操作日志保持一致。
- 复用当前门店选入能力，写入对应成品现货或配件仓库，状态为warehouse，不自动上架。
- 保留既有价格、库存、媒体引用、代际、日志和快照规则，不用原型的简化对象替代真实门店商品创建。
- 清单成功移除与单项结果可靠记录同属一致性处理，避免仓库已成功但结果丢失后再次创建。
- 旧选择接口单次上限100件是现有技术约束，不得静默截断整份清单；协调层可按现有能力分块执行并汇总为一个批次结果。

### 9.2 同门店多员工并发去重

**业务唯一范围：门店＋商品类型＋来源商品ID。**

1. 员工甲、乙可各自将同一商品加入个人清单。
2. 点击加入门店后，在单项事务内重新检查该门店是否已有该商品，回收站记录同样阻止再次加入。
3. 并发时以数据库事务串行化及有效唯一约束兜底，不能仅前端检查或先查后无保护插入。
4. 只有一个操作成功；另一个操作失败，原因固定为“该商品已加入门店，请勿重复添加。”
5. 判定以实际成功写入为准，不以谁先点击按钮为准；前一事务回滚不能使后一项错误地永久失败。
6. 失败项计入失败数，保留在后提交员工清单中，更新已加入门店状态并禁止再次提交，允许移除。
7. 不覆盖先成功记录，不重复生成仓库记录、成功日志或快照；其他商品继续处理。

当前迁移历史存在商品代际唯一键，不能假设最初store_id＋product_id唯一键仍是现行约束，也不能删除既有代际能力。实施需核对完整迁移后的实际结构，在事务内覆盖上述业务唯一范围，保留原有彻底删除与合法重选规则。

### 9.3 请求幂等和结果反馈

- 同一提交使用稳定request_id；按钮加载期间禁止重复发起。相同请求重传返回原批次及原结果，不再次执行。
- 员工之间不同请求命中同一商品，不按同一个幂等请求处理，应按9.2返回后一项失败。
- 网络中断不宣称全部失败或成功，通过批次结果查询确认实际进度和结果。
- 采用已确认的系统批量反馈样式：总数量、成功数量、失败数量；满足total = success + failure，处理中项未结算前不伪报完成。
- 明细只显示失败商品类型、商品名称、失败原因，不展示成功明细或旧版补充说明段落。
- 全成功使用现有成功反馈；部分/全部失败按标准结果弹框展示统计及失败明细。
- 服务端返回业务错误码和可读原因；唯一键冲突等内部错误应转成准确业务失败，不暴露SQL或堆栈。

| 错误码建议         | 用户原因示例                     |
| ------------------ | -------------------------------- |
| ALREADY_IN_STORE   | 该商品已加入门店，请勿重复添加。 |
| SOLD_OUT           | 该商品已售完，无法加入门店。     |
| SOURCE_UNAVAILABLE | 商品已下架，无法加入门店。       |
| NO_TYPE_PERMISSION | 无配件维护权限，无法加入门店。   |
| PRICE_INCOMPLETE   | 按既有价格配置校验返回具体原因   |
| ITEM_UNAVAILABLE   | 商品当前不可用，无法加入门店。   |
| PROCESSING_FAILED  | 加入失败，请稍后重试。           |

未知内部异常只影响当前项；认证失效、组织不合法等批次级问题应终止继续处理，并可靠保留已完成结果。

## 10. 数据与接口实施契约

### 10.1 建议的数据模型

| 数据         | 关键字段与约束                                                                                                               |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 清单记录     | id、tenant_id、store_id、account_id、product_type、source_product_id、added_at；归属＋类型＋商品唯一；归属＋时间＋ID查询索引 |
| 加入批次     | id、request_id、发起账号/门店/租户、状态、提交/结束时间、总/成功/失败数量；同一归属request_id唯一                            |
| 批次明细     | batch_id、清单记录ID、类型、商品ID、结果、错误码、原因、成功listing_id；每批每商品唯一                                       |
| 既有门店商品 | 复用成品/配件现有表，不另造统一仓库表；保留代际、日志和快照关系                                                              |

清单不是商品数据副本。商品名称、媒体、价格和状态按合法实时来源读取；仅批次审计需要时保存必要名称快照。时间由服务端产生并按项目时区标准处理。

### 10.2 建议接口

统一前缀建议`/api/admin/store-product-center`，遵守现有ApiResponse、认证、分页及错误响应约定。

| 方法与路径                | 职责                                                                  |
| ------------------------- | --------------------------------------------------------------------- |
| GET /categories           | 返回按finished/accessory分开的1—4级平台分类树                         |
| GET /products             | 名称、分类类型及ID、类型集合、加入状态集合、分页；统一排序并返回total |
| GET /products/{type}/{id} | 当前门店可读详情、动态属性/规格、媒体、价格及操作状态                 |
| GET /selection            | 当前归属、指定类型的清单分页，返回两类全量数量及总数                  |
| POST /selection           | 按类型＋来源ID加入清单；服务端检查可加入条件，重复请求不新增          |
| DELETE /selection/{id}    | 仅移除当前合法归属的清单记录                                          |
| POST /join-batches        | request_id及上下文令牌，服务端固定合法清单快照并逐项处理              |
| GET /join-batches/{id}    | 返回状态、总/成功/失败数量和失败明细，用于正常反馈及网络恢复          |

请求不接受价格、库存、权限结论、商品名称或组织归属作为可信写入依据。分类ID须验证其类型与合法树范围。

列表每项至少返回type、id、name、image、sourceCreatedAt、门店适用价格范围、soldOut、addedToStore、inSelection、canAdd及不可加入原因。详情增加attributes、attributeDisplayOrder、specDimensions、SKU与salesAttributes/displayMode等既有真实字段。

### 10.3 前端与旧入口收敛

- 新建独立正式路由并复用第24版展示结构，接入真实服务；入口用新标签页打开，不能继续打开旧选择弹窗。
- 移除旧弹窗及仅被它使用的筛选、选中和详情调用，先检索真实消费者再清理，不能删除其他模块共用能力。
- 公共详情能力以数据适配和展示复用为主，不因选品中心需求改坏原管理详情。
- 加入成功通过现有刷新机制或同源事件通知原页，原页重新获得焦点时重新查询；消息只触发刷新，不能携带可信组织写入指令。
- 再次进入新页和切换身份均重新取数；任何结果失败不使用预览数据兜底。

# 方案一

成品现货上游失效与下游重新上架方案

整理日期：2026年10月8日。
状态：讨论方案备份，待与其他方案对比后决定；尚未授权实施。本文件不代表业务代码、数据库或现行规则已经调整。

## 目标与核心规则

采用单一路径处理上游下架或删除，避免自动恢复、价格迁移、配置继承等复杂分支。

同一商品以唯一且不可变的商品 ID 识别。上游一旦下架或删除，受影响端当前商品关联永久失效；上游重新上架也不会恢复旧关联。受影响端必须彻底删除本端旧记录，再按现有流程重新获取、配置和上架。

商品身份不变；本端旧经营记录结束，重新获取后重新开始。数据库内部关联编号不是新的商品 ID，也不增加用户需要理解的业务编号。具体表结构和编号实现留待选定方案后设计。

## 影响范围

| 触发操作                   | 受影响端                                           |
| -------------------------- | -------------------------------------------------- |
| 供应链下架或删除商品       | 运营管理平台、已经获取该商品的门店                 |
| 运营管理平台下架或删除商品 | 已经获取该商品的门店                               |
| 门店自行下架或删除商品     | 按现有本店流程处理，不反向影响供应链或运营管理平台 |

下架、删除包括删除至回收站及彻底删除。触发方自身操作仍走其现有流程；本方案限制的是受影响端的失效商品。普通编辑、调价、库存变化不在本方案中新增失效规则。

未来新增业务端时，按其明确的来源依赖确定受影响范围，沿用相同失效规则；不据此推断未确认的业务关系。

## 失效商品的展示和操作

- 失效记录保留在原 Tab，显示遮罩和明确原因，不自动移动、不悄悄隐藏。
- 可查看详情和已有日志；业务操作只允许彻底删除，不允许编辑、上架、放回仓库或删除至回收站。
- 失效商品即使原本就在回收站，也只允许彻底删除，不允许恢复。
- 失效状态必须明确持久记录，并能说明触发平台、原因和时间；不能仅根据上游当前状态或选取批次是否相同推断。
- 页面刷新后直接呈现失效状态；未刷新时的操作也必须由服务端检查，阻止越过失效限制，并更新页面遮罩。
- 批量上架、批量放回仓库等操作遵循同样限制；支持对失效商品批量彻底删除。具体批量提示沿用对应端现有规范，不新增部分成功规则。

## 上游恢复后的单一路径

1. 上游恢复可用，旧失效关联仍不可售，不解除其失效限制。
2. 受影响端彻底删除本端旧记录。
3. 来源满足现有获取条件后，受影响端重新获取该商品。
4. 使用当前商品、规格和价格，按现有流程配置并上架。

供应链重新上架后，运营管理平台必须完成自己的删除旧记录及重新上架流程；门店仍需独立删除旧记录，并在运营商品可获取时重新从商品中心选择。任一环节恢复都不会使下游旧关联复活。

本端旧记录未彻底删除前，不允许重新获取同一商品，避免同一端同时存在新旧有效关联。这里的彻底删除只结束本端经营记录及其当前配置，不代表删除其他端商品、历史日志或订单依据。

## 商品数据和价格

重新获取时使用来源当时最新的商品数据、SKU、指导价及适用价格规则。旧的本端手动价格和专属配置不自动继承，重新配置时执行现有校验。

不增加恢复比价、自动下架确认、旧配置迁移或自动恢复流程。旧失效记录的展示不得冒充为新一轮经营数据；历史详情和日志以留存的历史数据或快照为依据，具体保存结构实施前核对。

## 日志与订单

- 沿用现有供应链下架／删除、运营管理平台下架／删除日志，不重复新增同义的“来源失效”事件。
- 用户实际执行彻底删除、放入仓库、上架等操作时，沿用各自现有日志。
- 不产生自动恢复、自动继承配置事件。
- 历史日志保留当时商品和价格快照，不随重新获取或后续编辑变化。
- 失效阻止新的销售；已有订单继续依照下单时的商品、规格、价格快照处理，不能因本端彻底删除或重新获取而丢失依据、改变价格。

## 已有隐藏数据的处理边界

正式实施前先只读统计选取批次不匹配等隐藏记录，不直接批量恢复或清理。

- 只有旧记录、没有后续新关联的：恢复可见并明确标记失效，保留原所在 Tab，等待用户彻底删除。
- 已存在新旧关联的：单独列出数量、归属、配置与日志依赖，制定迁移处理方案后再执行；不能直接全部恢复或删除。
- 历史日志、订单依据及其他端数据必须保留。数据修复范围和迁移操作须在实施方案中明确，本次保存不授权这些操作。

## 取舍与对比依据

优势：失效不可逆、恢复路径统一，减少跨端自动同步分支；记录可见、状态明确，便于用户理解和技术维护。

成本：即使上游只是短暂下架且未改数据，所有受影响端也需重新获取和上架；接入端越多，操作总量和恢复经营所需时间越大。

当前讨论接受这一成本，以换取生命周期规则简单、保守、可预测。该规则控制的是商品生命周期复杂度，不意味着整个系统不会产生其他复杂度。

后续方案按以下方面比较：规则数量、跨端依赖、价格正确性、数据与日志可维护性、重新操作成本、已有订单保护和存量迁移风险。
